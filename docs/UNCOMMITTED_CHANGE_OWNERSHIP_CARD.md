# LifeScript Uncommitted Change Ownership Card

用于在 `git status --short --branch` 已显示工作区存在较多未提交改动、且 `npm run build` 与 `npm run lint` 已通过时，快速把一个更棘手的问题讲清楚：

> 如果下一轮是否继续改业务代码，已经取决于“当前这些未提交改动到底分别属于什么主题、哪些该保留、哪些该先不要碰”，应该如何先做人肉归属分拣？

它和现有文档的分工如下：

- `docs/HIGH_RISK_DIRTY_WORKSPACE_STOP_CARD.md`：回答“当前为什么更适合停手”
- `docs/COLLAB_HANDOFF_CARD.md`：回答“怎么把当前局面交接给下一位协作者”
- `docs/ITERATION_DIFF_OVERLAP_CHECK_CARD.md`：回答“继续进入某个已改文件前，是否会撞上现有 diff”
- **本文**：回答“在继续推进前，如何先把当前未提交改动按主题、风险层和保留策略做最小归属梳理”

一句话目标：

> 当继续自动迭代已经卡在‘现有改动归属不清’这一步时，先用一份低成本分拣卡把工作区局面理顺，而不是直接继续硬改。

---

## 1. 什么时候优先看这张卡

适合以下场景：

- 已执行 `git status --short --branch`
- 已确认当前分支仍是预期分支
- 已执行 `npm run build`
- 已执行 `npm run lint`
- 当前没有必须马上修的工程错误
- 继续推进前，已经需要回答“这些未提交改动到底是不是同一批、该不该一起保留”

如果当前工程验证未通过，先看 `docs/ITERATION_VERIFICATION_TRIAGE_CARD.md`；如果只是想决定这一轮要不要停，先看 `docs/HIGH_RISK_DIRTY_WORKSPACE_STOP_CARD.md`。

---

## 2. 这张卡解决的核心判断

继续推进前，先回答下面 3 个问题。

### 问题一：当前未提交改动，能不能按主题大致分组？

不是要求一次性判断到“最终该怎么提交”，而是至少先回答：

- 哪些更像同一条业务增强
- 哪些更像文档 / 说明补充
- 哪些是临时试验或还说不清意图的改动

如果连粗分组都做不到，就不适合继续自动进入业务代码。

### 问题二：哪些改动属于高敏感层？

优先标出以下高敏感层文件：

- `src/app/page.tsx`
- `src/app/api/chat/route.ts`
- `src/lib/memory.ts`
- `src/types/index.ts`
- `src/app/layout.tsx`
- `src/app/globals.css`

只要高敏感层文件已经和其它页面、文档改动混在一起，下一步就更应该先做归属判断，而不是继续顺手扩改。

### 问题三：哪些改动现在能明确“保留 / 暂缓 / 待判断”？

最少分成三类就够：

- **保留候选**：目标清楚、看起来是有意改动
- **暂缓触碰**：虽然可能有价值，但这一轮不应继续进入
- **待判断**：意图不清、边界模糊，不能自动替用户拍板

一句话原则：

> 归属分拣的目标不是立刻决定一切，而是先把“能安全继续的”和“必须停下确认的”分开。

---

## 3. 推荐的最小分拣顺序

### 第一步：先看路径层级，不急着下结论

先把 `git status --short` 结果按层级粗看：

1. 核心业务 / 状态层
2. 页面与组件层
3. 文档与说明层
4. 新增目录 / 新文件

这一步只做“归类”，先别急着决定取舍。

### 第二步：按“改动意图”给每组起临时名字

例如：

- 消息列表体验增强
- 聊天链路与记忆逻辑调整
- 演示 / 答辩文档补强
- 安全执行卡补充
- 尚未确认的试验性改动

要求不高，只要后续别人能大致看懂这组改动在做什么即可。

### 第三步：标记每组的风险层

可直接用三档：

- **低风险**：独立文档、提示语、空态、aria、索引补充
- **中风险**：单页面局部展示增强、轻量样式调整
- **高风险**：共享类型、状态恢复、API、主状态机、持久化结构

如果一组改动同时跨了高风险和低风险文件，不要因为里面也有文档就误判成低风险。

### 第四步：只输出“下一步动作”，不要马上执行破坏性整理

每组改动最后只需要先写出一个动作标签：

- **继续保留，暂不扩改**
- **可以继续补低冲突配套**
- **必须先人工确认**

在没有用户拍板前，默认不要做：

- `git reset --hard`
- 强推
- 重写历史
- 擅自删掉看不懂的未提交改动

## 4. 30 秒粗分模板

可直接照着整理：

```markdown
## 当前未提交改动粗分
- 组 1：{{主题名}}
  - 典型文件：{{files}}
  - 风险层：{{低 / 中 / 高}}
  - 当前判断：{{保留候选 / 暂缓触碰 / 待判断}}

- 组 2：{{主题名}}
  - 典型文件：{{files}}
  - 风险层：{{低 / 中 / 高}}
  - 当前判断：{{保留候选 / 暂缓触碰 / 待判断}}
```

只要能整理出 2~4 组，通常已经足够支撑下一步是否继续自动迭代的判断。

---

## 5. 哪些信号说明“已经不能再自动往下走”

命中任一条，就应停止并说明：

- 需要决定某组高风险改动到底保留还是回滚
- 需要把多个主题的未提交改动重新拆分后才能继续
- 需要为了继续改一个小点而先理解大量旧 diff
- 需要在两种以上实现路线中做取舍
- 你已经无法清楚区分“哪些是原有改动、哪些是本轮新增”

一句话判断：

> 当下一步的核心工作已经从“实现增量”变成“解释旧改动和做取舍”时，这一轮就不该继续自动拍板。

---

## 6. 适合继续做的动作，和默认不要做的动作

### 更适合继续做

- 把当前未提交改动按主题做一页粗分说明
- 给协作者留一条清晰的风险摘要
- 继续补独立文档、日志或通知模板
- 在不触碰高风险组的前提下，补局部说明性增强

### 默认不要做

- 直接进入高风险组继续改代码
- 试图在本轮顺手“整理干净”所有未提交改动
- 凭主观猜测删除不理解的修改
- 为了让工作区看起来更整齐而做历史重写

---

## 7. 最短通知 / 交接写法

```markdown
- 当前分支正确，build / lint 已通过
- 但工作区内未提交改动已跨越核心业务、样式与文档层
- 下一步是否继续推进，已取决于现有改动归属与保留策略
- 本轮更适合先做归属粗分，而不是继续扩大业务改动面
```

## 8. 和其它文档怎么连用

推荐顺序：

```text
先看 HIGH_RISK_DIRTY_WORKSPACE_STOP_CARD
  → 确认当前是否应停手
再看本文
  → 先把未提交改动按主题 / 风险层做粗分
再看 COLLAB_HANDOFF_CARD
  → 把当前结论交接给下一位协作者
如果未来要继续进入某个已改文件
  → 再看 ITERATION_DIFF_OVERLAP_CHECK_CARD
```

---

## 9. 一句话结论

当 LifeScript 当前工作区已经因为多组未提交改动而进入高风险脏状态时，最专业的下一步通常不是继续写代码，而是先把现有改动做一轮最小归属分拣，明确哪些能继续保留、哪些暂时别碰、哪些必须等人工判断。
