# Branch & History Safety Card

用于在自动迭代或人工补丁开始前，快速确认“当前分支是否适合继续推进、哪些 Git 动作绝不能做、什么时候必须停下说明”，避免把低风险迭代演变成高风险历史操作。

---

## 1. 先看什么

每轮开始前至少先看两件事：

```bash
git status --short --branch
git branch --show-current
```

建议用下面三个问题快速判断：

1. **我现在是不是在预期分支上？**
2. **工作区是否已经有较多未提交改动？**
3. **接下来这一步会不会逼近“改历史 / 强推 / 覆盖别人改动”的边界？**

只要第 3 个问题答案不够明确，就不应该继续做会影响历史或分支结构的动作。

---

## 2. 自动迭代中默认允许的动作

这些动作通常属于低风险范围：

- 查看当前分支与工作区状态
- 运行 `npm run build`、`npm run lint`、`npm run verify`
- 在当前工作区内做独立、小范围、可复验的改动
- 补充文档、优化提示文案、完善演示或自检材料
- 在不改变历史结构的前提下记录本轮结果

这些动作的共同特征是：

- **不改 Git 历史**
- **不改变分支拓扑**
- **不覆盖现有未提交改动的意图**
- **失败后容易回退到原状**

---

## 3. 自动迭代中默认禁止的动作

下面这些动作默认都不应由自动迭代直接执行：

- `git push --force`
- `git push --force-with-lease`
- `git rebase -i`
- `git reset --hard`
- `git checkout -- <file>` 或等价覆盖本地改动的动作
- 大范围 `git restore` / `git clean`
- 未经确认就切分支、改目标分支、整理提交历史
- 未经确认就执行可能影响他人协作基线的合并策略调整

一句话原则：

> **自动迭代可以补东西、修小问题、做复验，但不应该替用户改写历史。**

---

## 4. 看到这些信号时应立即停下

只要出现下面任一情况，就应该停止继续改动，并向用户说明原因：

### A. 分支不符合预期
- 当前不在约定分支上
- 当前分支看起来像临时实验分支，但上下文里没有说明用途
- 当前分支与远端关系异常，无法判断是否适合继续提交

### B. 工作区脏度过高
- 已有大量业务文件改动，且分不清哪些是本轮新增、哪些是既有修改
- 同一核心文件已经被明显深度修改，再继续叠加会放大冲突面
- 本轮目标需要跨多个关键页面、共享类型或状态逻辑

### C. 需要“选方案”而不是“修问题”
- 下一步存在两个以上合理方向，且各有取舍
- 改动会改变用户可见行为、排序规则、状态恢复方式或数据结构
- 做法涉及产品判断，而不是单纯工程补强

### D. 需要动历史才能继续
- 想通过强推、重写提交、覆盖工作区来换取“更干净”的状态
- 发现只有先丢弃部分现有修改，才能继续推进
- 需要先整理分支、合并历史或搬迁大批文件，才能继续

---

## 5. 建议的停手说明模板

如果必须停下，可以直接按这个结构说明：

```text
- 我先确认了当前分支与工作区状态。
- build / lint 的结果是：……
- 我原本准备继续做的低风险动作是：……
- 但我发现下一步会进入以下高风险边界：……
- 这一步需要你来权衡的点是：……
- 因此我先停止，不继续扩大改动范围。
```

这样可以把“为什么停下”说清楚，而不是只说一句“风险较高”。

---

## 6. 最适合继续推进的替代动作

当你判断“不能再碰分支/历史层动作”时，优先考虑这些替代项：

- 补一份独立文档
- 完善 README / 文档索引
- 增强自检、演示、答辩、交接类材料
- 记录当前验证结果与风险边界
- 把后续待权衡的问题整理成清单，而不是直接替用户决定

核心思路不是“必须继续改代码”，而是：

> **只要还能交付独立价值、且不放大历史风险，本轮自动迭代就仍然是有效的。**

---

## 7. 一句话原则

先确认分支，再看工作区，再做最小改动；任何一步一旦逼近“强推、重写历史、覆盖现有修改、需要用户做方案取舍”的边界，就立刻停下说明。
