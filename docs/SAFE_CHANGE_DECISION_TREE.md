# LifeScript Safe Change Decision Tree

用于在工作区已存在较多未提交改动时，快速判断这一轮自动迭代到底该“继续改代码”、还是“改文档/说明”、还是“先暂停”。

这份文档适合配合 `docs/AUTO_ITERATION_CHECKLIST.md` 与 `docs/TROUBLESHOOTING.md` 一起使用，帮助在比赛冲刺期维持积极推进，同时控制冲突与回归风险。

## 适用场景

当你遇到下面任意一种情况时，优先参考本决策树：

- `git status --short --branch` 显示工作区已经较脏
- `npm run build` 与 `npm run lint` 已通过，但还想继续推进
- 你觉得“还有空间可以优化”，但不确定应不应该再碰核心页面
- 你担心继续改动会和当前未提交业务修改产生交叉

---

## 一图判断

```text
开始
  ↓
先看 git status / 当前分支
  ↓
当前分支正确吗？
  ├─ 否 → 先停下，确认当前改动是否需要保留，再决定是否切回基线
  └─ 是
       ↓
先跑 build 与 lint
       ↓
是否存在明确工程报错？
  ├─ 是 → 只修首个明确、低争议、可立即复验的问题
  └─ 否
       ↓
工作区是否已经较脏？
  ├─ 否 → 可做小范围体验优化或小功能增强
  └─ 是
       ↓
这次改动是否必须碰核心业务逻辑？
  ├─ 否 → 优先做独立文档、演示辅助、提示文案、无障碍补充
  └─ 是
       ↓
是否需要在多个方案之间取舍，或可能覆盖现有未提交改动？
  ├─ 是 → 暂停，说明权衡点，等待人工决定
  └─ 否 → 只做最小改动，并立即复验
```

---

## 分步判断说明

## 1. 先判断是不是正确分支

推荐先执行：

```bash
git status --short --branch
git branch --show-current
```

如果当前不在演示基线分支上，不要为了继续推进而贸然整理历史、强推分支或覆盖现有改动。

更合理的动作是：

- 先确认当前修改是否属于本轮目标
- 先确认是否需要保留当前现场
- 再决定是否切回基线或单独整理

---

## 2. 先判断是不是工程问题，而不是“想优化”

推荐先执行：

```bash
npm run build
npm run lint
```

### 如果其中任一失败

本轮优先做：

- 首个明确报错的修复
- 范围小、可立即验证的问题
- 不需要引入额外结构变化的修补

此时不建议：

- 顺手扩大成重构
- 同时修多个不相关方向
- 把“修错”变成“顺便升级整个模块”

### 如果两者都通过

说明当前工程基线是稳定的。

接下来要判断的重点，不再是“能不能改”，而是“现在改哪里最安全、最值得”。

---

## 3. 工作区不脏时，可以做什么

如果当前工作区改动很少，且 build / lint 都通过，通常可以考虑：

- 范围明确的小体验优化
- 不改变主流程的小功能增强
- 局部轻度重构
- 文档与说明补充

但仍应遵循：

- 一次只做一个清晰目标
- 改完后立即复验
- 不为了制造“变化感”而扩大修改范围

---

## 4. 工作区较脏时，优先做什么

如果当前已有大量未提交业务与文档改动，最稳妥的思路不是“完全不做”，而是切换为低冲突推进模式。

### 优先推荐

#### 文档完善

例如：

- 演示手册
- 答辩说明
- 自检清单
- 恢复手册
- 风险边界说明
- 故障排查补充

#### 体验微调

前提是改动独立、争议小、不会碰核心状态机：

- 空状态文案更明确
- 按钮提示更清楚
- 无障碍标签补充
- 录屏场景下更易理解的反馈语

#### 小型展示增强

前提是不新增复杂状态结构：

- 已有数据的摘要展示
- 可解释性的补充信息
- 辅助演示的轻量提示

---

## 5. 哪些情况应该直接暂停

出现以下任一情况时，应停止自动扩展，并把权衡点说明清楚：

- 需要在多个方案之间做取舍
- 无法确认当前未提交改动的归属与意图
- 改动可能覆盖用户正在进行中的业务修改
- 需要修改主状态机、共享类型或恢复逻辑
- 为了一个小问题，已经开始连锁触发多文件联动修改

这时“暂停并说明”，本身就是更高质量的执行结果。

---

## 6. 一个简单的风险分层法

### 低风险：适合直接推进

- 独立文档新增或补充
- 无障碍信息增强
- 提示文案优化
- 空状态说明优化
- 已有能力的展示增强

### 中风险：先确认边界再推进

- 共享类型字段调整
- 搜索 / 筛选 / 排序规则变化
- 本地持久化行为变更
- 会影响多个页面的联动展示修改

### 高风险：默认不做

- 主状态机重写
- 核心数据模型重构
- 批量迁移文件结构
- 强推、回滚历史、覆盖现有业务改动

---

## 7. 一轮安全自动迭代的最小闭环

推荐始终保持这个顺序：

```text
看 git 状态
  → 跑 build / lint
  → 判断是否属于脏工作区
  → 选择低风险目标
  → 做最小改动
  → 再跑 build / lint
  → 记录结果
  → 主动通知
```

如果改动做完后，已经无法用一句话解释“这轮到底提升了什么”，通常说明本轮目标选得不够集中。

---

## 8. 一句话原则

在 LifeScript 的比赛冲刺阶段，“积极型自动迭代”不等于持续扩大代码修改；当工程验证已经通过而工作区又较脏时，优先交付独立、低冲突、可立即复用的说明增强或微改动，往往才是最稳妥、最专业的推进方式。
