# LifeScript Iteration Notification Template

用于在每轮积极型自动迭代结束后，快速整理一条可直接发送给协作者或自己留档的结果通知。

这份模板适合以下场景：

- build 与 lint 已经完成，需要把本轮结果说清楚
- 工作区较脏，不适合继续扩大核心业务代码改动
- 需要把“做了什么、没做什么、接下来建议什么”压缩成一段稳定表达
- 希望减少每轮手写通知时的信息遗漏

---

## 使用原则

一条好的迭代结果通知，至少要让接收方快速知道四件事：

1. 当前分支和工作区状态是否安全
2. 本轮做了什么低风险改动
3. build / lint 是否通过
4. 接下来是否适合继续改、继续补文档，还是应该先停下权衡

如果这四件事里有任何一项说不清，通知就还不够完整。

---

## 最短通知模板

适合 IM、群消息、快速同步：

```text
已完成一轮 LifeScript 积极型自动迭代。
当前分支：{branch}
工作区状态：{git_summary}
本轮改动：{change_summary}
验证结果：build {build_result} / lint {lint_result}
风险说明：{risk_note}
后续建议：{next_step}
```

---

## 标准通知模板

适合发给协作者、记录在任务评论或作为每轮固定回执：

```markdown
### 本轮自动迭代结果
- 分支：`{branch}`
- Git 状态概览：{git_summary}
- 本轮目标：{goal}
- 改动类型：{change_type}
- 具体改动：{change_summary}
- 验证结果：`npm run build` {build_result}；`npm run lint` {lint_result}
- 风险说明：{risk_note}
- 后续建议：{next_step}
```

---

## 推荐字段写法

### 1. Git 状态概览

建议写法：

- 工作区已有较多未提交业务与文档改动，本轮继续避免扩大冲突面
- 当前分支正确，但存在多个页面与样式相关改动，适合继续做独立低风险交付
- 工作区较干净，可考虑继续推进小型体验优化

避免写法：

- 状态正常
- 改了一些东西
- 大概没问题

这些表达都太模糊，不利于后续协作。

### 2. 改动类型

建议从以下枚举中选择，便于后续回看：

- 工程问题修复
- 体验优化
- 小功能增强
- 轻度重构
- 文档完善
- 零代码闭环

### 3. 风险说明

推荐关注：

- 是否触碰核心页面
- 是否触碰共享类型
- 是否改动恢复逻辑或本地存储
- 是否可能与现有未提交改动冲突

推荐写法：

- 本轮仅新增独立文档，未触碰核心页面与共享类型，冲突风险低
- 本轮仅做提示文案优化，未改变数据结构与交互主流程，回归风险可控
- 本轮修复范围局限在单文件，已完成 build / lint 复验

### 4. 后续建议

建议明确给出“继续推进方向”或“暂停条件”：

- 若工作区仍保持当前较脏状态，优先继续做文档、自检、答辩辅助类独立交付
- 若下一轮需要修改主流程或共享类型，应先厘清现有未提交改动的归属与边界
- 若要继续推进体验优化，优先选择单文件、可立即复验、无需方案权衡的微改动

## 三种常用场景示例

### 场景 A：build / lint 都通过，工作区较脏

```markdown
### 本轮自动迭代结果
- 分支：`feat/v12-unified-baseline`
- Git 状态概览：工作区已有较多未提交业务与文档改动，本轮继续避免扩大核心代码冲突面
- 本轮目标：完成固定检查，并补充一项独立、低风险、可立即复用的交付
- 改动类型：文档完善
- 具体改动：新增一份演示/协作辅助文档，帮助在不改代码的前提下提升复验和同步效率
- 验证结果：`npm run build` ✅；`npm run lint` ✅
- 风险说明：本轮未触碰核心页面、共享类型、状态机或恢复逻辑，冲突与回归风险低
- 后续建议：若后续工作区仍较脏，优先继续补强演示、自检、答辩、协作交接类独立文档
```

### 场景 B：build 失败并已修复

```markdown
### 本轮自动迭代结果
- 分支：`{branch}`
- Git 状态概览：工作区存在未提交改动，但本轮仅处理首个明确工程错误
- 本轮目标：修复 build 失败并恢复可验证状态
- 改动类型：工程问题修复
- 具体改动：定位并修复 {file_or_module} 中的 {error_type}
- 验证结果：`npm run build` ✅；`npm run lint` ✅
- 风险说明：修复范围局限在必要文件，未顺手扩大重构范围
- 后续建议：若后续还要继续自动迭代，优先做低争议、小范围、可立即复验的增强
```

### 场景 C：遇到需要权衡，选择暂停

```markdown
### 本轮自动迭代结果
- 分支：`{branch}`
- Git 状态概览：当前工作区已存在多组未提交改动，继续推进会与既有修改边界发生交叉
- 本轮目标：完成固定检查并评估下一步可行方向
- 改动类型：暂停说明
- 具体改动：未继续落地代码改动，因为下一步涉及多个方案取舍或现有改动归属判断
- 验证结果：`npm run build` {build_result}；`npm run lint` {lint_result}
- 风险说明：继续自动推进可能误覆盖现有业务改动或放大冲突面
- 后续建议：建议先由人工确认保留方向、改动边界或方案优先级后再继续
```

### 场景 D：build / lint 通过后，选择零代码闭环

```markdown
### 本轮自动迭代结果
- 分支：`{branch}`
- Git 状态概览：当前分支正确，但工作区已有较多未提交业务与文档改动，本轮继续避免扩大冲突面
- 本轮目标：完成固定检查，并判断是否存在收益明确且边界清晰的低风险动作
- 改动类型：零代码闭环
- 具体改动：本轮未新增代码或文档改动；在确认 `build` 与 `lint` 通过后，选择以记录、说明与通知结束本轮，避免在脏工作区中继续放大风险
- 验证结果：`npm run build` ✅；`npm run lint` ✅
- 风险说明：本轮主动避免触碰核心页面、共享类型、状态恢复逻辑与现有未提交改动边界
- 后续建议：若下一轮仍想继续推进，优先选择独立文档、单点文案或单文件微体验增强；若涉及方案取舍则先人工确认
```

## 与迭代日志的分工

- `docs/ITERATION_LOG.md`：适合沉淀完整轮次记录，便于长期追踪
- 本文档：适合快速产出“本轮执行结论通知”模板，强调信息完整和表达稳定

两者可以同时使用：

1. 先按本文模板整理一条结果通知
2. 再把更完整的结构化内容补充到迭代日志

---

## 一句话结论

当工作区较脏、时间又紧时，稳定、完整、低歧义的结果通知本身就是一种工程质量，它能显著降低后续协作、复验和临场沟通成本。
