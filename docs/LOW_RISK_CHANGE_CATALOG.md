# LifeScript Low-Risk Change Catalog

用于在自动迭代、录屏准备、答辩前自检或工作区已较脏时，快速挑选“可以继续推进、但不容易放大冲突面”的改动类型。

它不是让你机械地只做文档，而是帮助你在工程验证已通过的前提下，更稳定地判断：**这一轮什么值得做，什么应该先停下。**

---

## 使用前提

优先在以下前提成立时使用：

- 已执行 `git status --short --branch`
- 已确认当前分支
- 已执行 `npm run build`
- 已执行 `npm run lint`
- 当前没有需要先修复的明确工程报错

如果 `build` 或 `lint` 失败，先处理首个明确问题，不要拿这份目录替代工程修复顺序。

---

## 一、什么算“低风险改动”

在 LifeScript 当前阶段，可优先视为低风险的改动通常满足以下大部分条件：

- 改动目标可以用一句话清楚说明
- 不需要重写已有主流程
- 不需要覆盖或回滚现有未提交业务改动
- 不依赖多个方案之间的主观取舍
- 可以在本轮结束前用 `build` 和 `lint` 复验
- 即使本轮停止在这里，也能独立交付并说清收益

一句话判断：

> 低风险改动，不等于“没价值的小改动”，而是“收益明确、影响面可控、验证路径清晰的改动”。

---

## 二、推荐优先级

当工程检查通过但工作区较脏时，建议按下面顺序选目标。

### 1. 文档完善

最稳妥，适合优先选。

可做内容：

- 演示顺序卡
- 答辩追问速答卡
- 故障排查补充
- 自检清单
- 协作交接说明
- 结果通知模板
- 迭代记录模板
- 生产预演说明

适合原因：

- 与现有业务改动交叉少
- 收益容易表达
- 便于下一轮继续接手
- 复验成本低

### 2. 单点体验优化

只在影响面非常清楚时进行。

可做内容：

- 空状态提示更明确
- 按钮文案更符合演示语境
- 反馈语更可解释
- 无障碍标签补充
- 桌面端演示微交互细节优化

适合前提：

- 只改单个页面或单个组件
- 不需要联动修改共享类型
- 不改变核心状态流
- 本轮可快速人工验证

### 3. 小功能增强

可以做，但必须严格限制边界。

可做内容：

- 基于已有数据的轻量摘要
- 便于演示的快捷入口
- 帮助答辩解释的状态说明
- 不改变主路径的小展示增强

适合前提：

- 能明确列出受影响文件
- 不需要改主状态机
- 不需要改本地存储结构
- 不会与当前未提交业务改动形成大范围交叉

### 4. 轻度重构

只有在“重构收益非常明确且几乎零争议”时才做。

可做内容：

- 提取重复常量
- 局部命名清晰化
- 小范围重复逻辑收敛
- 与当前功能等价的微整理

必须满足：

- 不改行为语义
- 不扩大文件改动范围
- 不触碰核心共享结构
- 改完后很容易解释“行为没有变化”

## 三、默认应回避的内容

以下改动即使“看起来很有价值”，在积极型自动迭代里也默认不应直接推进：

- 主状态机大改
- 核心页面骨架重做
- 跨多个页面的共享类型联动调整
- 本地持久化结构修改
- 恢复逻辑重写
- 大规模样式体系调整
- 重命名大量文件或目录
- 强推、改历史、覆盖现有未提交改动

如果某项改动必须进入以上区域，本轮应暂停并说明原因，而不是继续自动扩展。

---

## 四、四个快速判断题

开始动手前，可快速问自己：

### 1. 这项改动的收益能否一句话说清？

可以，例如：

- 让演示前检查更快完成
- 让协作者更快理解本轮结果
- 让空状态更容易解释

如果说不清，说明目标还不够稳。

### 2. 这项改动是否会碰共享类型、状态恢复或主页面骨架？

如果会，默认暂停。

### 3. 这项改动是否会与当前未提交业务改动明显交叉？

如果会，默认暂停。

### 4. 这项改动是否能在本轮结束前完成复验？

如果不能，不适合作为本轮低风险目标。

## 五、推荐动作模板

### 模板 A：文档完善

- 补充一份用于 {{场景}} 的独立说明，降低 {{风险或成本}}

示例：

- 补充一份用于自动迭代选点的低风险改动目录，降低在脏工作区中误碰高冲突改动的概率

### 模板 B：体验优化

- 优化 {{页面/组件}} 的 {{空态/提示/反馈}}，让 {{收益}}

示例：

- 优化消息列表空状态提示，让首次演示时的讲述更顺畅

### 模板 C：小功能增强

- 基于已有 {{数据/状态}} 增加 {{轻量展示}}，帮助 {{目标}}

示例：

- 基于已有互动数据增加轻量摘要，帮助资料页更快讲出核心价值

### 模板 D：轻度重构

- 收敛 {{局部重复逻辑/常量/命名}}，降低 {{维护成本或理解成本}}

示例：

- 收敛局部重复状态文案常量，降低后续统一修改成本

---

## 六、建议的最小闭环

每轮至少完成以下闭环：

```bash
git status --short --branch
git branch --show-current
npm run build
npm run lint
```

并记录：

- 当前分支
- Git 状态概览
- 本轮目标
- 改动类型
- 具体改动
- 验证结果
- 风险说明
- 后续建议

---

## 七、一句话原则

当工作区已经较脏而工程验证仍然通过时，真正高质量的积极推进，不是继续扩大改动面，而是继续交付**低冲突、可解释、可复验、可接手**的结果。
