# Ahead 信号判断速卡

用于在 `git status --short --branch` 已显示当前分支相对远端存在 `ahead N` 信号，且 `npm run build` 与 `npm run lint` 已通过时，快速回答一个很实际的问题：

> 这个 `ahead N` 到底是在提示“本地已经积累了可交付增量”，还是在提醒本轮不要继续替用户拍板 push、改历史或扩大提交边界？

---

## 1. 什么时候使用

建议在以下条件成立时使用：

```bash
git status --short --branch
npm run build
npm run lint
```

并且你已经看到类似信号：

- `## feat/v12-unified-baseline...origin/feat/v12-unified-baseline [ahead 1]`
- `## some-branch...origin/some-branch [ahead 2]`
- 当前分支正确，但本地已经领先远端若干提交

一句话判断：

> `ahead N` 说明本地分支与远端分支的提交边界已经暂时分叉；它不是报错，但会直接影响“这轮还能不能继续自动推进到 push / 历史整理层”。

---

## 2. 它到底在提醒什么

当你看到 `ahead N` 时，最重要的不是“数字大不大”，而是下面三件事：

1. **本地已经存在尚未推送到远端的提交**
2. **当前工作区里的未提交改动，不一定和这批已领先提交属于同一主题**
3. **如果继续推进开始涉及 push、rebase、squash、拆分提交，就已经进入需要人工拍板的边界**

因此，`ahead 1` 和 `ahead 2` 并不自动等于危险，但它至少意味着：

- 本轮结果不能默认被解释成“还没发生任何提交层变化”
- 下一步若涉及同步远端，需要更清楚地区分“已有提交”与“本轮新增改动”
- 自动迭代更适合继续做**本地低风险增量**，而不是替用户决定如何整理提交历史

---

## 3. 最小判断顺序

### 第一步：先确认这是不是预期分支上的正常 ahead

优先问自己 4 个问题：

1. 当前分支是不是预期分支？
2. `ahead N` 对应的远端跟踪分支是否清楚？
3. 当前 `build` 与 `lint` 是否都已通过？
4. 本轮是否只是继续做本地低风险补丁，而不是要替用户处理推送策略？

如果前 3 个问题里有任一答案是否定，或者第 4 个问题答不上来，就不要继续扩大范围。

### 第二步：把 `ahead` 和工作区脏度一起看

更适合继续低风险推进的情况：

- 当前分支正确
- `build` / `lint` 已通过
- `ahead N` 明确，但本轮只准备做独立文档、单点说明增强或极小展示层补丁
- 你能清楚说明“本轮没有处理 push、rebase、强推或历史重写”

需要提高警惕的情况：

- `ahead N` 同时伴随多个核心业务文件未提交改动
- 你已经分不清哪些属于已提交历史、哪些属于当前工作区新增
- 继续推进需要顺手决定“现在要不要 push / squash / rebase”
- 你需要替用户判断本地领先的这几次提交是否应该保留原样

一句话原则：

> `ahead N` 真正抬高风险的，不是“已经领先远端”，而是“接下来的动作开始逼近提交策略与历史整理”。

### 第三步：只保留不触碰历史的动作

如果还要继续推进，优先只做下面这些动作：

- 记录当前 `ahead N` 信号及其影响边界
- 补一份独立文档、索引入口或日志记录
- 做单文件、低争议、容易复验的本地增量
- 在结果同步里明确写出“本轮未处理 push / 历史改写”

尽量避免：

- 自动执行 `git push`
- 自动决定是否 squash、rebase 或重写历史
- 因为已经 `ahead` 就顺手扩大到高风险业务代码
- 在没分清提交主题前继续叠加多个平行目标

---

## 4. 默认推荐动作

### 推荐动作 A：把它当作“提交边界提示”，不是待办事项

看到 `ahead N` 时，优先理解为：

- 本地已有提交层结果
- 当前回合更要守住低风险边界
- 自动迭代可以继续产出增量，但不要替用户处理同步策略

### 推荐动作 B：如果继续，只做本地可复验的小闭环

适合继续的典型情形：

- 本轮仍能停留在文档、说明、索引、日志或单文件微调层
- 改动完成后可直接复验 `build` / `lint`
- 通知里能明确区分“当前分支 ahead”与“本轮新增改动”

### 推荐动作 C：如果开始涉及提交策略，就停下说明

一旦你开始需要回答下面任何问题，就应暂停：

- 现在要不要 push？
- 要不要先整理历史？
- 这几个本地提交是否该 squash？
- 当前领先远端的提交边界是不是还合理？

这些都不属于自动继续拍板的范围。

---

## 5. 最短判断模板

```text
当前分支正确，build 与 lint 已通过，但 `git status --short --branch` 显示本地相对远端存在 `ahead N` 信号。这说明本地已存在尚未推送的提交边界；若本轮继续推进，应仅限于可本地复验的低风险增量，不自动处理 push、强推、rebase 或历史整理。
```

---

## 6. 最短通知模板

```markdown
- 当前分支：{{branch}}
- Git 状态：相对远端存在 `ahead N` 信号，且工作区 {{clean_or_dirty}}
- 验证结果：build ✅ / lint ✅
- 本轮交付：{{独立文档或低风险补丁}}
- 风险说明：`ahead N` 代表本地已存在未推送提交，因此本轮不自动处理 push、历史改写或提交策略
- 后续建议：若下一步涉及同步远端、拆分提交或整理历史，应先人工确认
```

---

## 7. 什么时候必须停下等人工判断

命中任一条即可停：

- 需要决定现在是否 push 到远端
- 需要判断 ahead 的提交是否要 squash、rebase 或重写
- 需要解释已有本地提交与当前未提交改动是否属于同一主题
- 继续推进将进入多个核心业务文件，并放大与现有提交边界的耦合
- 你已经不能清楚区分“本地已提交内容”和“本轮新改动”

---

## 8. 一句话结论

当 `git status --short --branch` 已显示 `ahead N` 时，最稳妥的做法通常不是把它当成“可以顺手继续处理 Git 同步”的信号，而是把它当成**提交边界已经存在、自动迭代应避免越过历史与推送决策线**的提醒；只有在继续动作仍然停留在本地、低风险、可复验范围内时，才适合继续推进。
