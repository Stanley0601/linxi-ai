# LifeScript Auto Iteration Checklist

面向积极型自动迭代的固定检查清单，适用于本地开发、录屏彩排、答辩前自检，以及工作区已存在较多未提交改动时的低风险推进。

## 使用时机

当你准备在 LifeScript 项目中做一轮“先检查、再最小改动、最后复验”的自动迭代时，优先使用这份清单。

尤其适用于以下场景：

- 当前工作区已经有不少未提交改动
- 你希望继续推进，但不想扩大冲突面
- 你需要先确认本轮更适合改代码还是补文档
- 你希望把本轮结果整理成可复用的记录或通知

---

## 1. 迭代开始前：先做固定检查

### Git 检查

```bash
git status --short --branch
git branch --show-current
```

确认重点：

- 当前是否仍在 `feat/v12-unified-baseline`
- 是否已经存在较多未提交业务改动
- 是否出现了新增但尚未纳管的文档、资源或配置

### 工程检查

```bash
npm run build
npm run lint
```

如果准备提交、发起 PR 或做完整演示前自检，可进一步执行：

```bash
npm run verify
```

---

## 2. 判断本轮应该做什么

### 当 build 或 lint 失败时

优先处理：

- 首个明确的工程报错
- 低争议、改动面小的问题
- 能立即复验的问题

不建议：

- 在修错过程中顺手大改结构
- 同时展开多个方向的重构
- 为了“顺便优化”而扩大修改范围

### 当 build 和 lint 都通过，但工作区较脏时

优先处理：

- 独立文档补充
- 演示 / 录屏 / 答辩辅助说明
- 故障排查、恢复手册、自检清单
- 无争议的提示文案优化
- 可解释、可立即验证的小体验增强

不建议：

- 修改主状态机
- 扩大到共享类型联动调整
- 重做本地存储或恢复逻辑
- 为了追求“看得见的大变化”而增加高风险改动

---

## 3. 单次自动迭代的推荐顺序

```text
查看 Git 状态
  → 运行 build 与 lint
  → 判断工作区是否较脏
  → 选择低风险迭代点
  → 做最小可交付改动
  → 重新执行 build 与 lint
  → 记录结果
  → 主动通知执行结论
```

---

## 4. 本轮改动选择清单

如果需要快速判断“接下来做什么更稳妥”，可直接按下面优先级选择：

### 第一优先级：文档完善

适合内容：

- 演示顺序与讲解手册
- 故障排查与恢复指引
- 自检清单
- 提交前说明
- 当前工程边界与风险提示

### 第二优先级：体验优化

适合内容：

- 空状态更清楚
- 提示文案更明确
- 结果反馈更可解释
- 无障碍标签补充
- 桌面端或录屏场景下更顺手的微交互

### 第三优先级：小功能增强

适合内容：

- 基于已有数据的轻量展示增强
- 不改变主流程的小统计信息
- 辅助演示的快捷入口
- 便于答辩解释的状态摘要

### 默认暂停的内容

出现以下情况时，先停下，不要继续自动扩展：

- 需要在多个方案之间做取舍
- 需要判断现有未提交改动该保留还是覆盖
- 修改会触碰主状态机、共享类型或恢复逻辑
- 修复方式会明显改变用户已在进行中的业务改动

---

## 5. 完成后最低复验要求

至少再次执行：

```bash
npm run build
npm run lint
```

并再次确认：

```bash
git status --short --branch
```

重点确认：

- 本轮仅新增了预期文件或最小必要修改
- 没有扩大到核心文件的大范围冲突
- build 与 lint 仍然通过
- 本轮收益能用一句话清楚说明

---

## 6. 建议记录格式

可将每轮结果按以下格式追加到迭代日志中：

```markdown
## YYYY-MM-DD HH:mm
- 分支：
- Git 状态概览：
- 本轮目标：
- 改动类型：
- 具体改动：
- 验证结果：
- 风险说明：
- 后续建议：
```

---

## 7. 一句话原则

在比赛冲刺阶段，积极型自动迭代并不等于不断扩大代码改动；当工作区较脏而工程验证已通过时，优先交付独立、低冲突、可立即复用的说明增强，本身就是高质量推进。
