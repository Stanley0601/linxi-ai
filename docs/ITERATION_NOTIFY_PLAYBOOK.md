# LifeScript Iteration Notify Playbook

用于把“每轮自动迭代结束后，无论成功、异常还是主动暂停，都必须发出结果通知”这件事标准化，避免执行闭环里只做了检查、改动、复验，却漏掉最后一步同步。

---

## 1. 什么时候该看这份文档

适用于以下场景：

- 正在执行一轮积极型自动迭代
- 已完成 `git status --short --branch`、`npm run build`、`npm run lint` 中的全部或部分动作
- 需要把本轮结果同步给自己、协作者，或作为后续继续推进的交接依据
- 需要明确：即使本轮没有成功落地改动，也不能省略通知

一句话原则：

> 通知不是“做完后顺手发一下”，而是自动迭代真正结束前的必做动作。

---

## 2. 哪三种结果都必须通知

### A. 成功完成一轮低风险迭代

例如：

- 修复了明确工程问题
- 完成了文档补充
- 做了一项单点体验优化
- 完成了 build / lint 复验

这时通知的作用是：

- 说明本轮做了什么
- 说明验证是否通过
- 说明本轮没碰哪些高风险区域
- 给下一轮留下明确接手点

### B. 发生异常，未能按计划完成

例如：

- `build` 或 `lint` 失败
- 项目目录缺失或磁盘未挂载
- 本地依赖、端口、环境变量或网络条件异常
- 改动后发现问题超出低风险边界，无法在本轮安全收敛

这时更不能不通知，因为接收方需要知道：

- 卡在什么环节
- 当前是否已停止继续扩改
- 是否已经回到安全状态
- 下一步建议怎么处理

### C. 主动暂停，本轮不继续改

例如：

- 工作区较脏，继续改业务代码会扩大冲突面
- 下一步需要在多个方案之间做取舍
- 会触碰共享类型、状态恢复逻辑或主状态机
- 无法判断现有未提交改动哪些该保留、哪些该回滚

这时通知的价值在于：

- 说明为什么“停下”反而是更安全的结果
- 避免后续协作者误以为这一轮忘了做事
- 帮助人工接管时快速进入正确判断上下文

---

## 3. 推荐发送时机

### 推荐顺序

```text
检查 Git 状态
  → build / lint
  → 做最小改动或决定暂停
  → 再次 build / lint
  → 记录
  → 主动通知
```

### 不建议的做法

- 还没跑验证就先发“应该没问题”式通知
- 已经失败了但不说失败点，只说“本轮暂未完成”
- 本轮决定暂停，却没有说明暂停原因和后续建议
- 以为“没有代码改动”就可以不通知

---

## 4. 一条通知最少要包含什么

无论成功、异常还是暂停，至少要说明下面 6 项：

1. 当前分支
2. Git 状态概览
3. 本轮目标
4. 本轮实际结果
5. build / lint 状态
6. 风险说明与下一步建议

如果缺了其中两项以上，后续接手者通常仍然需要二次追问。

## 5. 三种通知模板

### 模板 A：成功完成

```markdown
### 本轮自动迭代结果
- 分支：`{branch}`
- Git 状态概览：{git_summary}
- 本轮目标：{goal}
- 改动类型：{change_type}
- 具体改动：{change_summary}
- 验证结果：`npm run build` {build_result}；`npm run lint` {lint_result}
- 风险说明：{risk_note}
- 后续建议：{next_step}
```

### 模板 B：异常结束

```markdown
### 本轮自动迭代结果
- 分支：`{branch}`
- Git 状态概览：{git_summary}
- 本轮目标：{goal}
- 当前结果：本轮未完成，已停止继续扩大改动
- 异常位置：{failure_step}
- 异常说明：{failure_reason}
- 验证结果：`npm run build` {build_result}；`npm run lint` {lint_result}
- 风险说明：{risk_note}
- 后续建议：{next_step}
```

### 模板 C：主动暂停

```markdown
### 本轮自动迭代结果
- 分支：`{branch}`
- Git 状态概览：{git_summary}
- 本轮目标：{goal}
- 当前结果：本轮未继续落地改动，已主动暂停
- 暂停原因：{pause_reason}
- 验证结果：`npm run build` {build_result}；`npm run lint` {lint_result}
- 风险说明：{risk_note}
- 后续建议：{next_step}
```

## 6. 三个推荐写法

### 成功时怎么写更稳

建议强调：

- 做了什么
- 已完成复验
- 没碰什么高风险区域

示例：

> 本轮新增独立通知闭环文档，并补充 README、文档索引与迭代日志入口；`npm run build` 与 `npm run lint` 均已通过，未触碰核心页面、共享类型、状态机或恢复逻辑。

### 异常时怎么写更稳

建议强调：

- 卡在哪一步
- 是否已经停止继续扩改
- 现在最安全的下一步是什么

示例：

> 本轮在 `npm run build` 阶段发现明确报错，已停止继续新增改动，避免把问题与现有未提交业务修改混在一起；建议先单独收敛 build 错误，再决定是否继续自动迭代。

### 暂停时怎么写更稳

建议强调：

- 为什么暂停不是消极，而是边界控制
- 继续做下去会放大什么风险

示例：

> 本轮确认当前工作区已存在较多未提交业务改动，继续推进需要判断多种实现方案与保留边界；为避免误伤现有修改，选择在完成验证后主动暂停并同步结论。

---

## 7. 发通知前最后 20 秒自检

发送前快速确认：

- [ ] 已写清当前分支
- [ ] 已写清本轮目标
- [ ] 已写清是成功、异常还是暂停
- [ ] 已写清 build / lint 状态
- [ ] 已写清本轮没碰哪些高风险区域，或卡在哪个异常点
- [ ] 已给出下一步建议

如果这 6 项里仍有明显空缺，先补完再发。

## 9. 一句话结论

自动迭代如果没有把结果主动同步出去，即使 build、lint 和改动本身都做了，也还不算真正闭环。
