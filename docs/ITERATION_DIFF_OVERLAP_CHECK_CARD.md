# LifeScript Iteration Diff Overlap Check Card

用于在 `git status --short --branch`、`npm run build` 与 `npm run lint` 都已完成之后，进一步回答一个很实际的问题：

> 如果某个目标文件当前已经有未提交改动，或者你怀疑自己的下一步改动会撞上现有业务修改，是否应该先看 diff，再决定要不要继续进入？

它不替代 `docs/MODIFIED_FILE_REENTRY_CARD.md`，而是补上它前面的一步：

- `MODIFIED_FILE_REENTRY_CARD` 解决的是“**已经确认目标文件有改动后**，还能不能继续进去”
- **本文** 解决的是“**在正式继续修改前**，要不要先看 diff，以及看 diff 时重点判断什么”

一句话目标：

> 让后续每轮自动迭代在进入已修改文件前，先用最小成本识别“这次会不会和现有改动撞车”。

---

## 1. 什么时候优先打开这张卡

适用于以下场景：

- `git status --short --branch` 显示工作区不干净
- `build` 与 `lint` 已通过
- 你已经挑中了一个候选目标文件或组件
- 但你还不知道这个文件里的现有改动，是否会与下一步小改动发生重叠
- 你希望继续积极推进，但不想因为“没先看 diff”而误入高冲突区

一句话判断：

> 当你开始想“这个文件虽然改过，但我也许还能顺手补一点”时，先看 diff，而不是先改代码。

---

## 2. 它解决的核心判断

这张卡主要帮你先回答 3 个问题：

1. 当前目标文件里的已有改动，是不是和我想做的事情属于同一区域？
2. 这个文件里的修改，是简单文案 / 样式 / 局部展示调整，还是已经涉及状态机、共享类型、持久化、排序、数据结构？
3. 如果我继续进入，这一轮还能保持“低风险增量”，还是已经会开始放大冲突面？

如果这 3 个问题里有 2 个答不上来，就不适合直接继续改。

---

## 3. 什么时候必须先看 diff

命中任一条，就建议先看 diff：

- 目标文件当前已在 `git status --short` 里显示为修改状态
- 你准备继续进入的文件属于页面级组件或核心交互组件
- 你不能确认现有改动是不是已经碰到你想继续补的那块区域
- 你对“这个文件最近为什么被改过”没有明确把握
- 你开始出现“我先进去看看，应该问题不大”的心态

一句话原则：

> 只要目标文件已经脏了，而你又不能明确说出“我这次只碰哪一小块、且和现有改动不重叠”，就先看 diff。

---

## 4. 看 diff 时重点看什么

不需要做复杂审计，先抓下面 5 点：

### 1. 改动集中在文件哪里

先看现有变更主要落在：

- 顶部 import / 常量区
- 中部核心渲染逻辑
- 事件处理函数
- 本地状态 / hooks
- 底部样式 / 文案 / 辅助说明

如果你的候选改动也落在同一区域，风险就会上升。

### 2. 现有改动是否已经越过“低风险线”

看到下面内容时要提高警惕：

- 新增或调整共享类型
- 新增状态字段或恢复逻辑
- 修改排序、筛选、持久化、数据映射
- 改动 API 请求、核心回调、主流程控制
- 多处片段同时一起变更，已经不像单点补丁

如果 diff 已经呈现这些特征，本轮通常不适合再顺手加一层。

### 3. 你的候选改动是否只是“边缘增量”

更适合继续的情况：

- 只补一个空态说明
- 只补一个 aria 标签
- 只补一段已有数据的解释文案
- 只补一个轻量提示，不改控制流
- 只补一个展示层小卡片，不改已有状态来源

如果候选改动开始需要改判断分支、数据来源或多个函数联动，就不再是边缘增量。

### 4. diff 是否已经难以 30 秒看懂

如果你在 30 秒内还看不明白“这份 diff 正在做什么”，通常就说明：

- 当前文件不适合继续作为低风险目标
- 或者至少不适合在这一轮继续进入

### 5. 这次继续进入后，是否还做得出干净的风险说明

问自己一句：

> 如果这一轮做完，我能不能清楚地说“我只新增了什么，没有碰什么高风险区域”？

如果做不到，说明不该继续。

---

## 5. 快速结论分层

### A. 可以继续进入

满足大部分条件时可继续：

- diff 范围局部
- 现有改动与你的目标区域基本不重叠
- 候选改动只影响展示层或提示层
- 不需要动共享类型、状态机、持久化或 API 行为
- 你能在一句话里讲清这次只新增什么

推荐动作：

- 继续做单点、局部、可复验的小增量
- 做完后重新跑 `build` 与 `lint`
- 在日志和通知里明确写出“本轮没碰什么”

### B. 先停在文档或别的文件

满足任一条时更建议换目标：

- diff 与候选改动区域明显重叠
- 现有改动已经牵涉状态、排序、恢复或数据结构
- 需要先读较长上下文才能判断是否安全
- 看完 diff 后仍然不能明确边界

推荐动作：

- 不继续进入这个文件
- 改做独立文档、索引补丁或更边缘的单文件微增强
- 在结果同步里说明“本轮主动避开已有改动重叠区”

### C. 必须停下并等待人工权衡

命中任一条就应停止：

- diff 显示多个方案正在并行尝试
- 继续进入需要理解另一批文件的配套改动
- 需要判断某段现有改动应保留、回滚还是重做
- 继续下去会触碰共享结构或核心交互策略
- 你已经需要问“这里到底想做成哪种行为”

这时正确动作不是硬做，而是停下并说明原因。

---

## 6. 推荐最短检查顺序

如果你只想做 30 秒判断，按下面顺序：

1. 先确认目标文件是否已修改
2. 看 diff 是否集中在与你候选改动相同区域
3. 看 diff 是否已涉及状态、持久化、共享类型或 API 行为
4. 判断你的候选改动是不是纯展示层边缘增量
5. 能继续就做；不能继续就换目标或停下

---

## 7. 可直接复用的最短记录模板

```markdown
- 目标文件：`{file}`
- 是否先看 diff：是
- diff 判断：{local_or_complex}
- 本轮决定：{continue_or_skip}
- 原因：{why}
```

示例：

```markdown
- 目标文件：`src/components/MessageListPage.tsx`
- 是否先看 diff：是
- diff 判断：现有改动已覆盖筛选、搜索与状态提示区域
- 本轮决定：跳过该文件
- 原因：继续进入会与当前未提交业务改动重叠，超出低风险边界
```

## 8. 与其他文档的分工

- `docs/ITERATION_GIT_STATUS_SIGNAL_CARD.md`：先判断当前工作区与分支整体是否安全
- `docs/LIFESCRIPT_SAFE_TOUCHPOINT_MAP.md`：先挑哪些文件更适合碰
- `docs/MODIFIED_FILE_REENTRY_CARD.md`：确认目标文件已改过后，进一步判断还能不能继续进入
- `docs/SAFE_SINGLE_FILE_UI_ENHANCEMENTS.md`：已经确定可继续进入时，筛选更合适的单文件微增强目标
- **本文件**：卡在“要不要先看 diff、看 diff 后应得出什么结论”这一步时优先使用

---

## 9. 一句话结论

在 LifeScript 当前这种 `build` / `lint` 已通过、但工作区已较脏的阶段，先看 diff 再决定是否继续进入某个文件，往往比“先顺手改一点再说”更能守住低风险自动迭代的边界。
