# LifeScript Iteration Execution Card

用于在每轮积极型自动迭代开始与结束之间，快速对照“现在该做什么、绝对不要做什么、什么时候必须停下说明”的执行速卡。

这份卡片适合以下场景：

- 先做固定检查，再决定本轮是否继续推进
- 工作区已经存在较多未提交改动，不适合扩大冲突面
- 需要把“积极推进”和“安全停手”同时标准化
- 需要在每轮结束时快速产出一条清楚、可复验、可通知的结果

---

## 1. 每轮开始的固定顺序

```text
看分支与 Git 状态
  → 跑 build
  → 跑 lint
  → 判断是否属于脏工作区
  → 选择低风险动作
  → 做最小改动或选择零代码闭环
  → 再次 build / lint
  → 记录结果
  → 主动通知
```

如果这个顺序被跳过，后面的“积极迭代”就很容易变成“无边界地继续改”。

---

## 2. 先问自己的 5 个问题

在真正动手前，先快速回答：

1. 当前分支还是不是目标分支？
2. 工作区里是否已经有较多未提交业务改动？
3. `npm run build` 和 `npm run lint` 现在是否通过？
4. 本轮候选改动是否能一句话说清收益？
5. 这项改动如果现在不做，是否会影响演示、录屏、答辩或后续协作效率？

如果第 4 和第 5 问都答不上来，通常说明这轮不该继续扩大改动范围。

---

## 3. build / lint 结果对应动作

### 情况 A：build 或 lint 失败

优先做：

- 修第一个明确报错
- 只修能直接复验的问题
- 修完立即重新验证

不要做：

- 借修错顺手重构
- 同时处理多个方向问题
- 为了“顺便优化”而扩大影响面

### 情况 B：build 和 lint 都通过，但工作区较脏

优先做：

- 文档完善
- 演示 / 答辩 / 协作辅助材料
- 无争议的提示文案优化
- 单文件、可复验、可解释的微体验增强
- 如果没有收益明确且边界清晰的低风险动作，允许本轮以“完成验证 + 说明停手原因 + 主动通知”零代码闭环收尾

默认避免：

- 主状态机调整
- 共享类型扩散式修改
- 本地存储与恢复逻辑改写
- 会影响现有未提交改动边界的功能修改

---

## 4. 本轮最稳妥的候选动作

当你需要快速决定“做什么更安全”，优先从上到下选择：

### 第一档：独立文档

例如：

- 演示检查卡
- 迭代结果通知模板
- 自检清单
- 风险边界说明
- 协作交接手册

### 第二档：低争议体验增强

例如：

- 空状态文案更清楚
- 操作反馈更明确
- 无障碍标签补充
- 演示场景下更顺手的轻量提示

### 第三档：已有数据的展示增强

例如：

- 小型统计摘要
- 演示辅助入口
- 可解释性增强的状态说明

如果候选动作不在这三档里，默认先停下，再判断。

---

## 5. 必须停止并说明的信号

出现以下任一情况，就应该停止自动推进，并明确说明原因：

- 需要在多个方案之间做取舍
- 无法判断当前未提交改动哪些应该保留
- 下一步会触碰主状态机、共享类型或恢复逻辑
- 修改会明显改变用户正在进行中的业务改动
- 需要强推、改历史、批量覆盖现有内容才能继续

一句话判断：

> 只要下一步不再是“低风险、可立即复验、无明显争议”，就不该继续自动扩张。

---

## 6. 每轮结束前的最小闭环

至少确认以下事项都完成：

- 已重新执行 `npm run build`
- 已重新执行 `npm run lint`
- 已再次查看 `git status --short --branch`
- 已能用一句话说明本轮收益
- 已明确说明本轮没碰什么高风险区域
- 若本轮选择零代码闭环，已明确说明“为什么这次不继续改动也是更安全的结果”
- 已主动发送结果通知

如果最后一步“通知”没有做完，这轮执行就还没有真正闭环。

---

## 7. 推荐通知骨架

```markdown
### 本轮自动迭代结果
- 分支：`{branch}`
- Git 状态概览：{git_summary}
- 本轮目标：{goal}
- 改动类型：{change_type}
- 具体改动：{change_summary}
- 验证结果：`npm run build` {build_result}；`npm run lint` {lint_result}
- 风险说明：{risk_note}
- 后续建议：{next_step}
```

---

## 8. 一句话原则

积极型自动迭代的关键，不是每轮都把代码改得更多，而是每轮都能在安全边界内稳定地产生一个可复验、可说明、可复用的小结果。
