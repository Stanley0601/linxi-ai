# LifeScript Zero-Change Wrap-up Card

用于在 `git status --short --branch`、`npm run build` 与 `npm run lint` 都已完成，但当前工作区已经较脏、不适合继续碰业务代码、也暂时没有明显不重复的文档缺口时，快速判断为什么**这一轮最专业的动作是零改动收尾**。

它解决的不是“还能不能再做一点”，而是一个更容易被忽略的问题：

> 当固定检查已经通过，但继续落手只会放大交叉风险时，怎样把“本轮不新增改动”也做成一个清晰、可交付、可通知、可复用的结果？

---

## 1. 什么时候优先看这张卡

适用于以下场景：

- 已执行 `git status --short --branch`
- 已确认当前分支仍是预期基线分支
- 已执行 `npm run build`
- 已执行 `npm run lint`
- 工作区里已经存在较多未提交的业务文件、样式文件、页面文件或文档文件改动
- 你还想继续积极型自动迭代，但候选动作要么明显会碰已改文件，要么与现有文档高度重叠，要么收益不足以覆盖新增风险

一句话判断：

> 当继续新增改动的收益已经不如“把边界说清楚并稳稳停住”的收益时，本轮就适合零改动收尾。

---

## 2. 它要解决的核心误区

很多自动迭代回合在 `build` / `lint` 都通过之后，最容易出现的误区不是“不会做”，而是：

- 觉得既然验证都过了，就应该顺手再补一点
- 觉得这一轮如果没有新增文件或代码，就不算积极推进
- 看到工作区已经很脏，但仍然想靠再做一小步来证明没有停住

现实里，更稳妥的判断通常是：

- 当前风险主要不在于有没有候选项，而在于候选项会不会与现有未提交改动发生交叉
- 当前真正缺的可能不是“又一份新补丁”，而是一次明确的停手说明
- 零改动不等于没结果；**完成检查、确认边界、主动通知、稳定停手** 本身也是一轮可交付闭环

---

## 3. 什么时候应该优先零改动收尾

命中以下任意两类及以上信号时，优先考虑本轮不再新增改动：

### A. 工作区脏度已经偏高

典型信号：

- 多个核心页面、组件、样式或类型文件已处于修改状态
- 文档目录也已存在一批新增或修改文件
- 继续进入任何单个文件，都可能碰到现有未提交 diff

### B. 工程验证已通过

说明当前最有价值的事情已经从“先恢复可构建”切换成“不要把已稳定的局面重新放大”。

最低信号：

- `npm run build` ✅
- `npm run lint` ✅

### C. 候选动作不够独立

典型信号：

- 需要继续进入已修改文件才能完成
- 需要联动多个页面或共享类型
- 需要判断现有未提交改动的归属后才能继续
- 需要在多个实现方案间做取舍

### D. 文档候选项已接近饱和

典型信号：

- 你能想到的主题在现有 `docs/` 中大多已经有对应入口
- 新增文档很可能只是换个标题重复已有内容
- 写完以后不容易说清“以后什么时候该打开它”

一句话原则：

> 当下一步已经更像“找理由继续改”，而不是“明确存在一个独立且低冲突的增量交付”，就该优先零改动收尾。

---

## 4. 零改动收尾仍然算完成了什么

本轮即使不新增代码或文档，也并不等于空转。至少已经完成了下面这些高价值动作：

1. 确认当前分支是否正确
2. 确认当前工作区脏度与风险级别
3. 完成 `build` 与 `lint` 验证
4. 识别出本轮不应继续扩改的原因
5. 主动输出结果通知，而不是让本轮静默结束
6. 为下一轮提供明确起点：继续前应优先做什么、不应直接做什么

换句话说：

> 零改动收尾交付的是“经过验证的当前局面 + 清晰的停手边界 + 下一轮的进入条件”。

---

## 5. 推荐动作顺序

如果判断应以零改动结束本轮，建议按下面顺序完成：

1. 再确认一次当前分支与 `git status --short --branch` 结论
2. 记录 `npm run build` 与 `npm run lint` 结果
3. 用一句话说明为什么本轮不继续新增改动
4. 明确写出本轮**没有碰什么高风险区域**
5. 给出下一轮建议：优先文档 / 单文件微增强 / 先人工权衡
6. 主动发出结果通知

推荐写法：

```markdown
- 当前分支正确，但工作区已较脏
- build / lint 已通过
- 本轮未继续新增代码或文档改动
- 原因：继续推进将进入已修改文件、共享类型或高重叠区域，收益不足以覆盖风险
- 风险边界：本轮主动避免触碰核心页面、状态恢复逻辑、共享类型与历史操作
- 后续建议：下一轮若继续推进，优先选择独立文档、单文件微文案或先人工确认边界
```

---

## 6. 什么情况下不要硬把它包装成“成功改动”

以下情况不建议把本轮描述成“已完成新的功能增强”或“又补了一项独立交付”：

- 实际上没有新增任何稳定成果
- 只是重复跑了一遍检查
- 只是看了几份文档，但没有形成新的明确输出
- 继续扩改本来就需要人工拍板，但你试图靠模糊措辞略过这个事实

更稳妥的表达应该是：

- 本轮完成了固定检查与风险评估
- 本轮基于当前脏工作区状态，主动选择零改动收尾
- 本轮结果是“确认可构建 + 明确停手边界 + 主动同步后续建议”

这样做的价值在于：

- 不夸大成果
- 不掩盖风险
- 让下一轮接手者知道现在该从哪里继续判断

---

## 7. 最短通知模板

### 模板 A：标准零改动收尾

```markdown
### 本轮自动迭代结果
- 分支：`{branch}`
- Git 状态概览：{git_summary}
- 本轮目标：完成固定检查并评估是否仍存在独立、低冲突的增量动作
- 当前结果：零改动收尾
- 验证结果：`npm run build` ✅；`npm run lint` ✅
- 风险说明：当前工作区已较脏，本轮主动避免继续进入已修改文件、共享类型、状态恢复逻辑或其他高重叠区域
- 后续建议：下一轮若继续推进，优先选择独立文档、单文件微增强；若涉及多方案取舍则先人工确认
```

### 模板 B：需要强调“不是失败，而是主动停手”

```text
本轮已完成固定检查，build/lint 均通过；由于当前工作区已较脏，继续新增改动会放大与现有未提交修改的交叉风险，因此本轮主动以零改动收尾，并同步后续建议。
```

---

## 8. 停手后下一轮优先看什么

如果下一轮还要继续，推荐优先按下面顺序重新判断：

1. `docs/ITERATION_RESUME_PROTOCOL.md`
2. `docs/ITERATION_GIT_STATUS_SIGNAL_CARD.md`
3. `docs/SAFE_CHANGE_DECISION_TREE.md`
4. `docs/SAFE_DOC_PATCH_PLAYBOOK.md` 或 `docs/LIFESCRIPT_SAFE_TOUCHPOINT_MAP.md`

如果下一轮开始前工作区仍旧同样脏，而候选项仍然不够独立，那就继续优先保守收尾，而不是为了“显得在推进”而硬做新增改动。

---

## 9. 一句话结论

在 LifeScript 当前这种“分支正确、build/lint 通过、但工作区已较脏”的阶段，零改动收尾不是消极停止，而是把**验证、判断、边界与通知**做成一次清晰、专业、可复用的低风险交付。
