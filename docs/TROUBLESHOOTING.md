# LifeScript Troubleshooting Guide

面向本地开发、演示录屏、答辩前自检的常见问题排查手册。

## 适用原则

当项目已经进入比赛冲刺阶段，排查问题时建议遵循以下顺序：

1. 先确认当前分支与工作区状态
2. 再执行 `npm run lint` 与 `npm run build`
3. 优先处理可复现、影响明确、改动面小的问题
4. 如果当前工作区已有较多未提交改动，优先避免扩大修改范围

---

## 1. 我不确定当前是不是正确分支

### 现象

- 不确定自己是否还在统一基线分支上
- 担心演示时混入了其他实验性改动

### 排查命令

```bash
git status --short --branch
git branch --show-current
```

### 建议处理

推荐继续在以下分支上做比赛演示和低风险迭代：

- `feat/v12-unified-baseline`

如果当前不在该分支，不要急于强推或重写历史，先确认当前改动是否需要保留，再决定后续整理方式。

---

## 2. `npm run build` 或 `npm run lint` 之前就发现工作区很脏

### 现象

- `git status` 显示很多已修改文件
- 不确定这些改动是否都属于同一个目标

### 建议处理

优先做以下动作：

- 新增独立文档
- 完善说明文件
- 修复范围非常明确的小问题
- 避免修改核心聚合文件或主状态机

不建议在这种情况下直接做大范围重构、批量重命名或跨文件结构调整。

---

## 3. `npm run build` 失败

### 常见原因

- 类型定义新增后，引用位置没有同步更新
- 轻量体验改动影响到共享类型或状态结构
- React 19 相关写法触发新的编译或类型问题

### 排查顺序

1. 先阅读报错中的首个 TypeScript 错误
2. 检查最近改动是否涉及共享类型
3. 检查新增枚举值、联合类型、可选字段是否全链路同步
4. 再看是否为渲染路径或状态更新方式引发的问题

### 特别提醒

LifeScript 当前工程里，以下问题出现过且值得优先怀疑：

- 新增类型枚举值后，没有同步更新所有引用位置
- 在 effect 里做不合规的同步 `setState`
- 异步回调中的类型收窄写法不安全
- 渲染路径中直接调用随机值导致不稳定输出

### 建议处理

- 优先修复第一个明确错误，不要同时进行大范围“顺手重构”
- 修复后重新执行：

```bash
npm run build
```

---

## 4. `npm run lint` 失败

### 常见原因

- 新增变量未使用
- 条件分支写法可进一步收敛
- hooks 或依赖数组不满足规则
- JSX 可访问性标签不完整

### 建议处理

- 先修复确定无争议的问题
- 不要为了消除 lint 报错而引入更复杂的逻辑
- 如果某个警告的修复方式会牵涉较大行为变化，应暂停并重新评估收益

### 推荐命令

```bash
npm run lint
```

如果 lint 已通过，就不要为了“看起来做了很多事”而继续扩大改动范围。

---

## 5. 页面能启动，但演示路径不顺

### 常见表现

- 不知道先展示哪个页面
- 现场操作步骤过长
- 找不到合适的讲解顺序

### 建议处理

优先保住主链路：

1. 消息列表
2. 主动消息 / 聊天页
3. 动态页
4. 资料页或结局页

如果只能展示一个核心亮点，优先展示：

- **主动消息 + 关系推进**

更完整的演示顺序可参考：

- `docs/DEMO_RUNBOOK.md`

---

## 6. 搜索、筛选或“继续上次演示”看起来不对

### 可能原因

- 浏览器保留了旧的本地状态
- 上次演示留下了搜索词、筛选模式或草稿缓存
- 当前演示路径与本地持久化状态叠加，导致页面表现与预期不一致

### 建议处理

先确认这是不是“功能失效”，还是“本地状态影响了当前展示结果”。

如果页面仍可正常操作，通常优先把它解释为：

- 演示状态被本地记忆保留
- 这是为了下次录屏或答辩更快恢复现场

如果确实影响当前展示，可以考虑：

- 手动清空搜索词
- 恢复默认筛选
- 切回消息列表主视图后重新进入目标页面

---

## 7. 聊天接口表现不稳定

### 现象

- 回复速度波动
- 模型返回内容不理想
- 现场网络不稳定时担心影响演示

### 建议处理

如果这次演示重点是产品流程，而不是模型能力本身，可以直接使用本地剧情链路或兜底表现完成展示。

推荐优先确认：

- 页面是否能顺利进入聊天主流程
- 当上游模型异常时，是否仍有温和 fallback
- 是否可以不依赖实时高质量生成也完整讲清产品价值

如果只是录屏或答辩预演，稳定性通常比“单次回复特别惊艳”更重要。

---

## 8. 我担心自动迭代改动过大

### 自检问题

在准备提交或继续扩展前，可以先问自己：

- 这次改动是否真的能立即验证价值？
- 是否触碰了核心状态机或共享数据结构？
- 是否会和当前未提交改动产生明显冲突？
- 是否存在更小、更安全的交付方式？

### 更稳妥的替代方案

当上述问题无法快速回答时，优先选择：

- 文档完善
- 空状态文案优化
- 无障碍补充
- 演示提示增强
- 现有信息的展示增强

---

## 9. 提交前最小自检

```bash
git status --short --branch
npm run lint
npm run build
```

如果要做更完整的一次确认：

```bash
npm run verify
```

### 什么时候优先用 `npm run verify`

以下场景更适合直接执行一键验证，而不是手动分步检查：

- 准备提交代码或发起 PR 之前
- 刚完成一轮低风险自动迭代，想快速确认没有引入回归
- 答辩、录屏或 Demo 彩排前，需要一次性确认工程状态
- 修改里同时涉及类型、样式与页面交互，担心只跑单项检查不够完整

### 如果 `npm run verify` 失败，应该怎么处理

建议按输出中最先出现的问题处理，不要同时展开多条修复线：

1. 先修首个明确错误
2. 修完后重新执行 `npm run verify`
3. 如果仍失败，再看下一条报错

这样更适合比赛冲刺期的小步快跑，也能降低和现有未提交改动互相干扰的风险。

建议至少确认以下事项：

- 当前分支正确
- 本次改动范围足够小、能说明收益
- 没有覆盖已有未提交业务改动
- lint 通过
- build 通过
- 演示主链路仍可讲述

## 11. 工作区已经有很多改动，还要继续自动迭代怎么办

### 建议判断顺序

如果 `git status --short --branch` 已经显示当前工作区存在较多未提交改动，但你仍希望继续做一轮积极型自动迭代，建议按下面顺序判断：

1. 先确认当前分支是否仍为演示基线分支
2. 先执行 `npm run build` 与 `npm run lint`
3. 如果两项都通过，优先做低冲突动作，而不是继续深入核心业务逻辑
4. 如果发现接下来需要覆盖、取舍或重组现有未提交改动，应暂停并先厘清边界

### 更适合继续做的内容

在这种场景下，通常优先考虑：

- 补充独立文档或手册
- 完善答辩、录屏、自检相关说明
- 增强明确无争议的空状态、提示文案或无障碍信息
- 记录本轮检查结论，方便后续协作者快速接手

### 不建议继续做的内容

除非已经明确当前未提交改动的归属与意图，否则不建议继续：

- 扩大到核心状态机修改
- 调整共享类型并跨文件联动修改
- 批量重构页面结构或状态恢复逻辑
- 为了“做点什么”而新增破坏性改动

### 一条简单判断规则

如果当前工程验证已经通过，而你又不确定现有未提交业务改动是否会被影响，那么最安全、最积极的做法通常不是继续碰核心代码，而是做一项可以独立交付、可立即复用、且不会放大冲突面的文档或说明增强。

## 12. build 和 lint 都通过了，但还想继续积极型自动迭代怎么办

### 适用场景

你已经完成固定检查，并得到类似结果：

- `git status --short --branch` 显示当前分支正常
- `npm run build` 已通过
- `npm run lint` 已通过
- 工作区里仍然存在较多未提交业务改动

这时最容易出现的误区不是“没事可做”，而是为了继续推进而贸然扩大改动范围。

### 推荐判断顺序

建议继续按下面顺序判断下一步：

1. 先问这次迭代是否必须改业务代码才能体现价值
2. 如果不是，优先选择可以独立交付的低冲突改动
3. 如果需要碰核心页面、共享类型或状态恢复逻辑，先确认现有未提交改动的归属和边界
4. 如果仍无法快速判断影响面，宁可停在文档、说明和演示辅助层，也不要为了“积极”而扩大风险

### 更适合继续推进的方向

在 `build` 和 `lint` 都已经通过的前提下，通常更值得优先做的是：

- 补充演示、录屏、答辩、自检类文档
- 增强故障排查说明、风险边界说明和恢复手册
- 优化已有功能的提示文案、空状态表达和可解释性
- 记录本轮验证结论，帮助后续协作者快速接手

### 暂时不建议继续推进的方向

如果你还不确定现有未提交改动是否会被影响，通常不建议继续：

- 修改主状态机或核心导航流
- 调整共享类型并联动多文件同步修改
- 大范围重构消息、聊天、动态等核心页面
- 为了新增“看得见的变化”而引入额外状态或数据结构

### 一句话原则

当 `build` 与 `lint` 都已经通过，而当前工作区又较脏时，最积极的做法不一定是继续碰核心代码；能够独立交付、立即复用、且不会放大冲突面的说明增强，本身就是一次高质量自动迭代。

---

## 13. 结论

对于当前 LifeScript 项目，最稳妥的排查方式通常不是“立即大改”，而是：

- 先确认分支与工作区状态
- 先跑 `lint` / `build`
- 先定位首个明确问题
- 优先做低风险、小范围、可解释的修复

如果工程验证已经通过，而工作区又存在较多未提交改动，那么新增独立文档、完善演示说明或补齐故障排查信息，往往就是最合理的一次积极型自动迭代。
