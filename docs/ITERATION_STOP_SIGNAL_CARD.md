# LifeScript Iteration Stop Signal Card

用于在每轮积极型自动迭代中，快速判断“现在是不是该停下了”，避免在 `build` / `lint` 已通过、工作区又较脏的情况下，因为还想再多做一点而把低风险回合推进成高风险回合。

这份卡片不负责告诉你“先做什么检查”，也不负责替你“挑本轮目标”，而是专门回答一个很关键、却最容易被忽略的问题：

> 这一轮什么时候继续推进是专业，什么时候及时停手反而更专业？

---

## 1. 什么时候该看这份卡片

适用于以下场景：

- 已执行 `git status --short --branch`
- 已确认当前分支
- 已运行 `npm run build`
- 已运行 `npm run lint`
- 你已经完成一项低风险改动，或正在犹豫要不要继续顺手再做一点
- 你感觉“似乎还可以再推进”，但又担心会扩大冲突面

一句话原则：

> 自动迭代最常见的失误，不是一开始就选错方向，而是在已经足够安全收尾的时候没有停下。

---

## 2. 为什么“知道何时停下”是独立能力

在 LifeScript 当前阶段，很多轮自动迭代都发生在下面这种上下文里：

- 当前分支正确
- 工作区已经存在较多未提交业务与文档改动
- `build` 与 `lint` 都已通过
- 还存在一些看上去也值得优化的小问题

这时真正危险的，不是完全不做事，而是：

- 因为“还有一点时间”继续顺手扩改
- 因为“这也不算大改吧”开始联动多个文件
- 因为“都已经改到这了”把文档回合做成代码回合
- 因为“只是统一一下”扩大到共享类型、样式或状态逻辑

所以，“是否继续改”本身需要单独判断，而不应该只靠直觉。

---

## 3. 最常见的 5 个停手信号

出现以下任一信号，就应优先考虑停止继续自动扩改。

### 信号 1：本轮已经形成独立交付

例如：

- 已新增一份完整独立文档
- 已修复一个明确工程问题并完成复验
- 已完成一个单点体验优化，收益可以一句话说清
- 已完成记录与通知闭环

一句话判断：

> 当本轮已经可以清楚回答“这次交付了什么”，继续加改就不再是必需动作。

### 信号 2：下一步开始碰多个文件

如果你原本只是想：

- 调整一处提示文案
- 补一份说明文档
- 做一个小体验增强

但做着做着发现需要继续改：

- 另一个组件
- 共享类型
- 顶层页面状态
- 本地存储或恢复逻辑

这通常说明你已经跨过低风险边界。

### 信号 3：开始出现“顺手一起改了”的念头

典型危险信号包括：

- “这个也顺手统一一下”
- “这里一起整理一下更好看”
- “反正都在这个文件里”
- “把这一块一并重构掉算了”

这类想法最大的问题不是一定错，而是它们通常意味着：

- 改动目标开始扩散
- 收益边界开始变模糊
- 本轮已不再是一个清晰、低争议的单目标回合

### 信号 4：下一步需要主观权衡

例如：

- 两种交互写法都说得通
- 不确定当前未提交改动该保留还是回滚
- 不确定是优先演示体验、还是优先工程整洁
- 不确定要不要调整已有功能边界

只要进入方案取舍，本轮就不再适合继续自动推进。

### 信号 5：你已经无法用一句话说清“再改的收益”

如果你已经说不清下一步到底是在提升什么，例如：

- 是为了演示稳定性？
- 是为了答辩表达？
- 是为了工程通过率？
- 还是只是为了再多改一点？

那通常说明现在最正确的动作就是停下。

---

## 4. 三个高频停手场景

### 场景 A：工作区较脏，但工程验证通过

建议动作：

- 完成记录
- 主动通知
- 停止继续扩大改动面

原因：

- 继续做代码修改的收益通常不如风险边界清晰
- 这类场景更适合把本轮收住，而不是继续扩展

### 场景 B：刚做完一项低风险文档交付

建议动作：

- 如果没有新的、同样独立且边界明确的候选动作，直接停下

原因：

- 文档交付往往已经构成完整成果
- 再顺手碰代码，最容易让“低冲突回合”变成“混合回合”

### 场景 C：刚修完 build / lint 报错

建议动作：

- 如果首个明确问题已经修复并复验通过，本轮默认停止
- 只有在下一项候选动作仍然明显低风险、低争议时，才考虑继续

原因：

- “修错成功”不等于“适合顺手再做一轮增强”
- 首个明确问题收敛后，最重要的是维持安全状态

---

## 5. 30 秒停手判断法

如果你只想用最短时间做判断，可直接按下面流程：

```text
本轮是否已有独立成果？
  否 → 可继续选一个低风险目标
  是 → build / lint 是否通过？
        否 → 先收敛验证问题
        是 → 下一步是否会扩大到多个文件或需要方案权衡？
              是 → 停下并说明
              否 → 再问一次：新增收益是否非常明确？
                    否 → 停下并说明
                    是 → 才考虑继续
```

如果你在最后一步仍然犹豫，默认停下更安全。

---

## 6. 停下时应该怎么表述

“停下”不是“本轮没做成”，而是应该明确说明：

1. 已完成什么
2. 为什么现在继续做风险更高
3. 下一步建议是什么

推荐写法：

```markdown
- 当前分支正确，工作区已存在较多未提交业务与文档改动
- 本轮已完成固定检查与一项独立低风险交付
- `npm run build` / `npm run lint` 均已通过
- 继续推进将扩大核心改动交叉面，因此本轮在完成记录与通知后主动停手
```

这种表达会比“先这样吧”清楚得多。

---

## 8. 一句话结论

积极型自动迭代真正成熟的标志，不是每轮都多改一点，而是能在收益已经成立、风险即将上升的那个点上，及时停下并把结果说明白。
