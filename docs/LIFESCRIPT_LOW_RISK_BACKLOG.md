# LifeScript Low-Risk Backlog

用于在 `build` / `lint` 已通过、但工作区已经较脏时，快速挑选**仍然值得继续推进**的低风险目标。

它和 `docs/LOW_RISK_CHANGE_CATALOG.md` 的区别是：

- `LOW_RISK_CHANGE_CATALOG` 解决的是“**哪类改动**通常更稳妥”
- 本文解决的是“**LifeScript 当前这个项目**接下来还有哪些更具体、可直接落地的低风险候选项”

换句话说，这是一份更贴近当前页面、组件与演示场景的候选 backlog，而不是抽象原则表。

---

## 使用前提

建议仅在以下条件同时成立时使用：

- 已执行 `git status --short --branch`
- 已确认当前分支是预期分支
- 已执行 `npm run build`
- 已执行 `npm run lint`
- 当前没有必须优先修复的明确工程报错
- 你希望继续积极推进，但又不想误碰高冲突区域

如果当前工程验证没有通过，先修第一个明确报错，不要先来挑 backlog。

---

## 一、这份 backlog 的目标

这份文档优先收录以下候选项：

- 收益可以一句话说清
- 影响面能提前大致圈定
- 不需要改主状态机
- 不需要重写本地存储结构
- 不依赖多个实现方案之间的主观取舍
- 即使这一轮停在这里，也能独立交付并说清价值

一句话原则：

> 低风险 backlog，不是“最小、最无聊”的 backlog，而是“在当前项目阶段依然有价值、但不容易放大冲突面”的 backlog。

---

## 二、优先选择顺序

当工作区较脏且工程验证已通过时，建议按下面顺序从上往下挑：

### 1. 文档 / 演示支持增强

优先级最高。

典型收益：

- 让后续自动迭代更容易选点
- 让录屏与答辩讲解更稳定
- 让协作者更快接手当前基线

### 2. 单页面文案 / 空态优化

适合只改一个页面或单个组件的提示语、说明语、空状态文案。

### 3. 基于现有数据的轻量展示增强

适合“数据已经有，只是还没被更好展示出来”的小增强。

### 4. 局部轻度重构

仅在“几乎零争议、行为等价、文件范围可控”时进行。

---

## 三、按页面划分的候选 backlog

下面的候选项并不要求一轮做完，而是帮助后续每一轮更快挑选一个**更具体**的低风险目标。

---

## 1. 消息列表页（`MessageListPage`）

### 适合继续做的候选项

- 进一步增强搜索结果为空时的引导文案，让用户知道下一步是“清空搜索”“切回全部”还是“换关键词”
- 给快捷视图或筛选胶囊补充更明确的状态说明，降低首次演示时的解释成本
- 在不改排序规则的前提下，补充“当前排序 / 当前筛选”的轻量提示
- 优化桌面端键盘提示的可见性，让 `/`、`⌘/Ctrl + K`、`Escape` 更容易被发现
- 补充无障碍描述，让固定、静音、未读等状态对读屏更友好

### 默认先别碰的边界

- 排序规则大改
- 搜索命中逻辑重写
- 与本地持久化强绑定的筛选状态结构调整
- 需要联动多个页面共享类型的改动

### 最小复验建议

- 搜索正常
- 快捷视图切换正常
- 键盘操作仍可用
- `npm run build` / `npm run lint` 通过

---

## 2. 聊天页（`ChatView` / `ChatBubbles`）

### 适合继续做的候选项

- 进一步优化输入区提示语，让“还能输入什么”“为什么建议这样回”更容易理解
- 补充发送前后的微反馈文案，例如剩余字数、建议回复用途说明
- 改善建议回复区域的辅助提示，使其更像“演示助理”而不是单纯按钮组
- 优化空态或首轮开场引导，让首次进入聊天页时更容易组织讲述顺序
- 补充轻量无障碍标签，让消息区、输入区、建议区语义更清楚

### 默认先别碰的边界

- 主动消息消费链路
- 聊天推进状态机
- 角色关系阶段逻辑
- 任何需要改 Prompt 或回复生成核心结构的改动

### 最小复验建议

- 发送消息正常
- 建议回复正常
- 剩余字数与提示不冲突
- `npm run build` / `npm run lint` 通过

---

## 3. 动态页 / 空间流（`MomentsFeed`）

### 适合继续做的候选项

- 优化筛选栏提示，让当前模式更容易被用户一眼看懂
- 给恢复默认入口补充更明确的解释文案，降低“为什么会恢复”的疑惑
- 强化兴趣命中或关系命中的轻量说明，让动态排序更可讲述
- 优化空态提示，让“当前没有内容”变成“为什么没有、现在可以做什么”
- 补充更清楚的演示引导语，帮助答辩时快速说明动态页的价值

### 默认先别碰的边界

- 动态排序规则重写
- 动态数据结构调整
- 评论 / 点赞状态的持久化机制重构
- 跨页面共享记忆逻辑修改

### 最小复验建议

- 筛选可切换
- 恢复默认入口正常
- 关键动态仍可浏览
- `npm run build` / `npm run lint` 通过

---

## 4. “我的”页 / 资料页（`MyProfileTab` / `ProfilePage`）

### 适合继续做的候选项

- 补强本地数据摘要的解释文案，让“这些数据为什么值得展示”更容易说明
- 优化继续上次演示入口的提示，让用户更容易理解它适合何时使用
- 补充画像、偏好或统计卡片的辅助说明，让答辩时更容易自然过渡
- 增强资料页中状态摘要的措辞，让展示更像产品能力而不是调试信息
- 优化轻量空态或缺省说明，避免页面在数据较少时显得突兀

### 默认先别碰的边界

- 本地缓存数据结构调整
- 恢复入口逻辑重写
- 新增依赖多个数据源的大型统计模块
- 需要同步多个页面消费同一新字段的改动

### 最小复验建议

- “我的”页可正常打开
- 资料页核心信息仍可展示
- 继续上次演示入口不受影响
- `npm run build` / `npm run lint` 通过

---

## 5. 结局页 / 时间线页（`EndingView` / `TimelineView`）

### 适合继续做的候选项

- 优化总结卡片或收束文案，让“用户影响了什么”更容易一句话讲清
- 补充更清楚的阶段解释语，帮助观众理解时间线的意义
- 强化关键指标的展示提示，让结尾页更适合作为演示收束点
- 优化无障碍说明或辅助标题，让内容层级更清晰
- 增加轻量过渡提示，让从聊天页进入结局页的叙事更顺畅

### 默认先别碰的边界

- 时间线数据模型修改
- 结局判定逻辑重写
- 角色成长 / 关系演化算法调整
- 任何需要重新设计整体结局结构的改动

### 最小复验建议

- 结局页可正常展示
- 时间线仍可浏览
- 总结卡片文案无明显冲突
- `npm run build` / `npm run lint` 通过

---

## 6. 跨页但仍可控的轻量候选项

只有在范围仍然清楚时才考虑。

### 可以考虑

- 统一若干重复提示文案的措辞，让整体体验更一致
- 提取局部重复常量，降低后续微调成本
- 增补若干 aria 标签、标题层级或辅助说明，提升可访问性与可解释性
- 给已有功能补一层“为什么存在”的解释文案，增强答辩表达

### 不建议直接继续扩大的方向

- 统一改造多个页面的数据结构
- 批量调整共享类型并联动多个组件
- 为了“顺手更优雅”而扩大重构范围
- 一轮内同时做文案、交互、排序、持久化多种改动

---

## 四、适合直接复用的一句话目标模板

### 文档类
- 补充一份用于 {{场景}} 的独立说明，降低 {{风险或理解成本}}

示例：
- 补充一份用于后续自动迭代选点的项目化 backlog，降低在脏工作区下盲目选题的成本

### 文案类
- 优化 {{页面}} 的 {{提示 / 空态 / 辅助说明}}，让 {{收益}}

示例：
- 优化动态页恢复默认入口的辅助说明，让首次演示时更容易解释筛选为何变化

### 轻量展示类
- 基于已有 {{数据 / 状态}} 增加 {{轻量展示}}，帮助 {{演示 / 答辩收益}}

示例：
- 基于已有画像摘要补充更清晰的状态说明，帮助“我的”页更快讲出个性化价值

## 五、30 秒排除法

如果你不确定某个候选项是否适合当前这一轮，可以快速问自己：

1. 这项改动是否会碰共享类型、状态恢复或主状态机？
   - 会：先停下
   - 不会：继续问下一题

2. 这项改动是否会与当前未提交业务改动明显交叉？
   - 会：先停下
   - 不会：继续问下一题

3. 这项改动的收益能否一句话说清？
   - 不能：先换题
   - 能：继续问下一题

4. 这项改动能否在本轮结束前完成 `build` / `lint` 复验？
   - 不能：不适合作为当前轮次目标
   - 能：可以继续

---

## 六、推荐闭环

每轮从这份 backlog 中挑完目标后，仍建议完成最小闭环：

```bash
git status --short --branch
npm run build
npm run lint
```

并记录：

- 当前分支
- Git 状态概览
- 选中的 backlog 项
- 改动类型
- 验证结果
- 风险说明
- 后续建议

---

## 七、一句话结论

当 LifeScript 当前工作区已经较脏、但工程验证仍通过时，最好的积极型自动迭代，不是继续盲目扩大改动范围，而是从一份**贴近当前页面、收益可解释、边界可控制、复验可完成**的 backlog 里，选出本轮最值得做的一项。
