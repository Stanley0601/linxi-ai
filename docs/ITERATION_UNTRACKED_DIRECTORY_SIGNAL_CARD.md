# 未跟踪目录信号速卡

用于在 `git status --short --branch` 已显示 `?? docs/`、`?? .github/`、`?? some-dir/` 这类**未跟踪目录**信号，且 `npm run build` 与 `npm run lint` 已通过时，快速回答一个很实际的问题：

> 这些 `?? 目录/文件` 到底只是独立增量，还是已经把当前工作区推到了更高风险的一档？

---

## 1. 什么时候使用

建议在以下条件成立时使用：

```bash
git status --short --branch
npm run build
npm run lint
```

并且你已经看到了以下任一信号：

- `?? docs/`
- `?? .github/`
- `?? scripts/`
- `?? public/something/`
- `??` 条目明显不止 1~2 个，而是成组出现

一句话判断：

> `?? 目录/文件` 不只是“还没 add”，更代表这批内容的**边界、规模与归属**还没有被 Git 明确纳入当前上下文。

---

## 2. 它到底在提醒什么

当 `git status --short --branch` 出现 `?? 目录/` 时，最重要的不是“命令没报错”，而是下面三件事：

1. **这个目录里可能不止一个文件**
2. **这些文件可能属于一个完整主题，也可能只是很多零散残留**
3. **如果你还没看清目录内容，就很难判断继续扩改会不会放大范围**

因此，`?? docs/` 和 `?? .github/` 这类信号的风险，并不只取决于“是不是文档”，还取决于：

- 目录里的文件数量
- 文件之间是否围绕同一主题
- 是否会进一步牵动 README、业务代码、配置或 CI
- 你能否在 30 秒内解释清楚“这批未跟踪内容为什么存在”

---

## 3. 最小判断顺序

### 第一步：先确认它是“独立增量”还是“边界未明”

优先问自己 4 个问题：

1. 这个未跟踪目录里，文件是否大多围绕同一主题？
2. 这些文件是否大多是说明性材料，而不是业务代码、类型、状态机或 API？
3. 我是否能在不碰其它已修改核心文件的前提下，仅在这个目录内完成本轮动作？
4. 补完后，我能否一句话说明“这轮为什么停在这里”？

如果 4 个问题里有 2 个以上答不上来，默认不要继续扩改。

### 第二步：看它有没有把工作区脏度抬高一档

出现下面任一情况，可直接把风险判断上调：

- 未跟踪目录与多个核心业务文件同时存在
- 未跟踪目录里混有代码、配置、文档多种类型
- 目录本身是新增的，但还需要回头修改多个已修改文件给它补入口
- 你需要继续 `git add` / `git mv` / 补很多索引，才能证明这批内容是自洽的

一句话原则：

> 未跟踪目录不是天然高风险，但一旦它和核心文件、跨文件补入口、主题边界不清这几件事叠在一起，就应按更高风险处理。

### 第三步：只保留最独立的动作

如果还要继续推进，优先只做下面这些动作：

- 在同一个未跟踪目录里新增一份独立说明文档
- 补一条低冲突索引入口
- 追加一条结果记录或通知模板
- 用一句清晰结论把本轮停手理由写出来

尽量避免：

- 从未跟踪目录继续扩到核心页面
- 顺手改 README、共享类型、状态恢复逻辑、API 行为
- 为了“让目录看起来更完整”继续新增多份平行文档
- 自动替用户决定这批未跟踪内容该整体保留还是整体回滚

---

## 4. 看到 `?? docs/` 与 `?? .github/` 时怎么理解

这是 LifeScript 当前阶段特别常见的一种组合信号：

- 说明**文档体系或工程辅助材料可能正在集中补强**
- 也说明这批内容**尚未被正式纳入当前提交边界**
- 如果同时还有 `src/app/page.tsx`、`src/lib/memory.ts`、`src/types/index.ts`、`src/app/api/chat/route.ts` 等核心文件修改，就不应再把它简单理解成“只是多了两份文档”

更稳妥的结论通常是：

> 工程验证虽已通过，但当前工作区同时存在核心改动与未跟踪目录；这意味着继续扩改前，必须优先确认未跟踪内容的主题边界，而不是把它们当作“顺手再补一点”的低成本区域。

---

## 5. 默认推荐动作

### 推荐动作 A：先把它当成风险信号，而不是待办列表

不要一看到 `?? 目录/` 就默认进入“把它补完”的思路。

更好的起手式是：

- 先看目录里有什么
- 再判断是不是一个独立主题
- 最后才决定本轮是否继续在里面补一份最小成果

### 推荐动作 B：如果要继续，只在未跟踪目录内部做单点闭环

适合继续的典型情形：

- 目录内容边界清楚
- 本轮新增内容是单点、独立、说明性增强
- 不需要再碰现有已修改核心文件
- 不涉及方案权衡或 Git 历史操作

### 推荐动作 C：如果目录边界说不清，就停下说明

停手并不等于这轮失败。

相反，在 `??` 信号已经说明上下文边界不清时，能及时停住、把原因说清，本身就是高质量结果。

---

## 6. 最短判断模板

```text
当前分支正确，build 与 lint 已通过，但工作区除核心改动外还出现了未跟踪目录信号（如 `?? docs/`、`?? .github/`）。这说明新增内容的边界与归属尚未完全纳入当前提交上下文；若本轮继续推进，应仅限于目录内部的独立低冲突补丁，否则应主动停手并说明。
```

---

## 7. 最短通知模板

```markdown
- 当前分支：{{branch}}
- Git 状态：存在未跟踪目录信号（如 `?? docs/` / `?? .github/`），同时仍有核心文件修改
- 验证结果：build ✅ / lint ✅
- 本轮交付：{{独立文档或索引补丁}}
- 风险说明：未跟踪目录代表新增内容边界尚未完全收敛，因此本轮不继续扩大改动面
- 后续建议：先确认未跟踪目录内文件的主题归属与保留策略，再决定是否继续进入业务代码
```

---

## 8. 什么时候必须停下等人工判断

命中任一条即可停：

- 需要决定未跟踪目录整体是保留、拆分还是回滚
- 需要把目录内容接入多个已修改核心文件
- 需要在不同整理方式或提交边界之间做主观取舍
- 需要解释目录里哪些文件属于本轮、哪些属于历史残留
- 继续推进将跨入共享类型、核心页面、状态恢复或 API 逻辑

---

## 9. 一句话结论

当 `git status` 已出现 `?? 目录/文件` 时，最稳妥的动作通常不是把它当成“还可以顺手多做一些”的信号，而是先把它当成**边界尚未收敛**的提示；只有在目录内容独立、主题清楚、无需牵动核心改动时，才适合继续做单点低风险补丁。
