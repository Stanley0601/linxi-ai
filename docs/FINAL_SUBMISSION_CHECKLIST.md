# LifeScript Final Submission Checklist

面向比赛提交前、PR 发起前、录屏交付前的最终核对清单。

当 `npm run build` 与 `npm run lint` 已通过，但你还需要确认“这次交付是否已经足够稳、足够能讲、足够能交”时，优先使用这份文档。

## 适用场景

- 准备发起 PR 或整理 patch
- 准备提交比赛材料
- 准备录制最终演示视频
- 准备把当前版本作为答辩或展示基线

---

## 1. 先确认当前是否适合继续推进

先执行：

```bash
git status --short --branch
git branch --show-current
npm run build
npm run lint
```

如需在提交前做一轮完整工程自检，再执行：

```bash
npm run verify
```

建议先确认：

- 当前仍在目标分支，例如 `feat/v12-unified-baseline`
- `build` 与 `lint` 已通过
- 当前工作区虽然可能较脏，但你知道哪些改动属于本轮要交付的内容
- 没有需要先人工权衡的大改动或破坏性调整

如果以上任一项不满足，先不要进入“最终提交”动作。

---

## 2. 最终提交前必看四件事

### A. 工程是否可复验

至少确认：

- `npm install` 后可正常运行
- `npm run build` 通过
- `npm run lint` 通过
- 如本轮要交付给协作者或评委环境，最好补充 `npm run verify` 结果

如果当前问题只是视觉细节或文案润色，不要为了“最后再改一点”去打破已经通过的工程状态。

### B. 演示主链路是否仍可讲述

最少确认以下页面还能顺畅串起来：

- 首页 / 落地页
- 消息列表
- 聊天页
- 动态页
- 资料页或“我的”页
- 结局页或时间线页

如果不确定，可配合 `docs/SMOKE_TEST_MATRIX.md` 做一轮 3~8 分钟最小冒烟检查。

### C. 说明材料是否足够支撑协作

至少确认：

- `README.md` 中运行方式仍正确
- 新增的演示 / 自检 / 排查文档已纳入相关文档索引
- 本轮改动可以用一句话说清楚“做了什么、为什么做、风险在哪”
- 如存在本地状态或演示依赖，文档里有对应说明

### D. 这轮改动是否真的值得交付

可直接问自己四个问题：

1. 这轮改动是否提升了稳定性、讲述性或协作效率？
2. 这轮改动是否避免了高风险破坏性调整？
3. 这轮改动是否能被快速复验？
4. 这轮改动是否不会意外覆盖当前未提交的重要业务修改？

只要有两项答不上来，就先暂停，不要急着往前推进。

---

## 3. 比赛冲刺期的推荐提交流程

```text
检查 Git 状态与分支
  → 跑 build / lint / verify
  → 做 3~8 分钟最小冒烟验证
  → 确认 README 与相关文档索引完整
  → 记录本轮改动与验证结论
  → 再决定是否提交 / 发 PR / 录屏
```

这个顺序的重点不是“做更多事”，而是避免在最后阶段把本来已经稳定的版本重新搞乱。

---

## 4. 最小提交前核对表

可直接逐项过一遍：

- [ ] 当前分支正确
- [ ] `git status --short --branch` 已看过
- [ ] `npm run build` 通过
- [ ] `npm run lint` 通过
- [ ] 如有需要，`npm run verify` 通过
- [ ] 关键演示链路仍能讲述
- [ ] README 中运行命令与文档索引仍正确
- [ ] 本轮新增文档或功能有明确价值
- [ ] 没有为了追求“更完整”而引入高风险修改
- [ ] 可以用一句话向他人说明这轮交付收益

---

## 5. 不建议在最终提交前临时做的事

以下动作很容易在冲刺末期放大风险，默认不建议：

- 临时重构主状态机
- 批量调整共享类型
- 大范围改动本地持久化与恢复逻辑
- 顺手合并多个不相关优化
- 为了“看起来更厉害”再插入高不确定性功能
- 在没有完整复验前直接提交一批混合改动

一句话：

**提交前最值钱的，不是变化更多，而是可复验、可讲述、可协作。**

---

## 6. 30 秒极简判断法

如果时间很紧，可只问：

- 当前 build / lint 过了吗？
- 核心演示链路还顺吗？
- README 和文档入口还对吗？
- 这轮改动有清晰收益吗？

四项都能回答“是”，通常就已经具备进入最终提交准备的基础。

```markdown
- 风险边界：
- 是否适合继续提交：是 / 否
```

---

## 9. 一句话原则

在 LifeScript 当前阶段，最终提交前最稳妥的动作不是继续扩大改动，而是确认当前版本已经能稳定通过工程验证、顺畅支撑演示，并且留有清晰可复用的说明材料。
