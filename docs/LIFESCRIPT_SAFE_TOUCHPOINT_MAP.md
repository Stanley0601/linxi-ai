# LifeScript Safe Touchpoint Map

用于在 `build` / `lint` 已通过、但工作区已经较脏时，把“还能安全改哪里”进一步从抽象原则落到**具体文件 / 组件触点**。

它和已有文档的分工如下：

- `docs/LOW_RISK_CHANGE_CATALOG.md`：回答“哪类改动通常更稳妥”
- `docs/LIFESCRIPT_LOW_RISK_BACKLOG.md`：回答“当前项目还有哪些具体候选项”
- **本文**：回答“如果真要落到文件或组件，优先看哪里、哪些地方要谨慎、哪些地方默认别碰”

一句话目标：

> 当工作区已经较脏时，帮助后续自动迭代先找到**边界清楚、影响面更可控**的落点，而不是为了继续推进而误碰高冲突区域。

---

## 使用前提

建议仅在以下条件成立时使用：

- 已执行 `git status --short --branch`
- 已确认当前分支是预期分支
- 已执行 `npm run build`
- 已执行 `npm run lint`
- 当前没有必须优先修复的明确工程报错

如果 `build` 或 `lint` 失败，先修第一个明确问题，不要先用这份地图挑新目标。

## 一、怎么读这份地图

本文把触点分为三层：

### A. 相对安全触点

适合优先考虑：

- 单文件边界清楚
- 以文案、说明、无障碍、已有展示增强为主
- 不需要联动共享类型或状态恢复逻辑
- 本轮结束前容易复验

### B. 谨慎触点

不是绝对不能动，但要先想清楚：

- 是否会和当前未提交改动交叉
- 是否需要跨页面联动
- 是否会影响已有演示路径
- 是否需要用户在两个方案之间做取舍

### C. 默认别碰触点

在积极型自动迭代里默认不要主动进入：

- 主状态机
- 持久化结构
- 核心共享类型
- API 核心行为
- 任何会扩大到多文件联动的底层逻辑

## 二、相对安全触点（优先看）

### 1. `docs/`

**推荐程度：最高**

最适合在工作区较脏但又想继续积极推进时作为首选。

适合做的事：

- 新增独立说明文档
- 补充已有卡片的判断条件或模板
- 增补演示、答辩、自检、交接、通知类材料
- 整理更贴近当前项目的 backlog / 触点图 / 决策卡

适合原因：

- 不碰核心业务逻辑
- 与现有页面级改动交叉概率最低
- 收益容易表达
- 复验简单清晰

默认别做：

- 为了“统一风格”大规模重写所有文档
- 批量改标题、批量重命名文档
- 一轮里同时整理过多文档，导致本轮目标失焦

---

### 2. `README.md`

**推荐程度：高（仅限文档入口与说明性补充）**

适合做的事：

- 为新增文档补充入口
- 更新一条与当前已落地能力一致的说明
- 补充验证命令或文档导航

适合前提：

- 改动是增量性的
- 不重写整份 README 结构
- 能明确说明为什么这次必须补充

默认别做：

- 重新改写项目定位或大段产品叙事
- 在 README 中引入尚未落地的新能力描述

---

### 3. 单页面说明性组件文案

优先考虑以下组件中的**提示语、空态、辅助说明、aria 标签**，前提是改动保持单文件、单点、低争议。

#### `src/components/MessageListPage.tsx`

适合做：

- 搜索为空时的解释文案
- 当前筛选 / 当前排序的轻量提示
- 快捷键提示可见性优化
- 固定 / 静音 / 未读等状态的无障碍说明

默认别做：

- 搜索命中逻辑重写
- 排序评分机制改动
- 与本地持久化绑定的筛选状态结构调整

#### `src/components/ChatView.tsx`

适合做：

- 输入区提示语优化
- 建议回复区域的辅助说明
- 局部 aria 标签补充
- 首屏引导或说明文案微调

默认别做：

- 聊天推进逻辑修改
- 主动消息消费或状态切换链路改动
- 需要联动多处状态的交互重构

#### `src/components/MomentsFeed.tsx`

适合做：

- 筛选栏说明文案优化
- 恢复默认入口的解释性文案
- 空态说明增强
- 轻量演示提示补充

默认别做：

- 排序规则重写
- 点赞 / 评论相关持久化逻辑调整
- 跨页面记忆逻辑改动

#### `src/components/MyProfileTab.tsx`

适合做：

- 本地数据摘要说明文案
- “继续上次演示”入口的辅助解释
- 画像 / 统计卡片的讲解性补充
- 空态或缺省说明优化

默认别做：

- 恢复入口逻辑重写
- 本地缓存结构调整
- 新增依赖多个来源的大型统计模块

#### `src/components/EndingView.tsx`

适合做：

- 总结卡片的解释文案
- 结尾收束语优化
- 辅助标题与层级说明增强
- 演示友好的总结提示

默认别做：

- 结局判定逻辑改动
- 关键指标计算逻辑调整
- 与时间线数据联动的结构变化

#### `src/components/TimelineView.tsx`

适合做：

- 阶段解释语优化
- 内容层级标题补强
- 无障碍或讲解性文案补充

默认别做：

- 时间线数据模型调整
- 阶段排序或生成逻辑重写

## 三、谨慎触点（能不碰就不碰）

### 1. `src/components/ProfilePage.tsx`

原因：

- 容易与 `MyProfileTab`、结局态展示、角色资料信息形成联动
- 看似只是展示页，实际可能牵涉多块信息组织

适合做：

- 极小的说明性文案补充
- 不影响数据消费方式的标题微调

暂停信号：

- 需要新增字段
- 需要与其他页面统一展示结构
- 需要调整已有资料组织顺序且存在多种方案

---

### 2. `src/components/BottomTabBar.tsx`

原因：

- 导航组件影响面天然更广
- 容易牵动多个页面体验与演示路径

适合做：

- 极小的 aria 标签补充
- 不改变导航语义的提示优化

默认别做：

- 导航结构调整
- 新增入口
- 标签语义大改

---

### 3. `src/app/layout.tsx` / `src/app/globals.css`

原因：

- 任何全局样式或布局调整，都可能影响多个页面
- 在脏工作区里很容易放大回归面

适合做：

- 非常局部、确定不会外溢的说明性微调

默认别做：

- 全局 spacing / color / typography 批量调整
- 影响多个页面的布局修复
- 为了统一视觉而扩大范围的改动

---

## 四、默认别碰触点（当前自动迭代优先回避）

### 1. `src/app/page.tsx`

这是当前项目的主应用状态机级入口之一。

默认别碰原因：

- 很容易牵动主流程
- 影响多个页面状态切换
- 与恢复逻辑、演示主链路耦合度高

只有在以下条件同时成立时才考虑：

- 问题明确且必须修
- 影响面能说清
- 不存在多个方案待权衡
- 用户不需要先做产品或技术取舍

否则默认停下。

---

### 2. `src/lib/memory.ts`

默认别碰原因：

- 与本地持久化结构、恢复路径、演示状态直接相关
- 改动后很可能需要多页面联动复验

这类文件一旦改动，就不再属于“低风险顺手补一刀”的范围。

---

### 3. `src/types/index.ts`

默认别碰原因：

- 共享类型一旦变化，影响面往往不是单文件
- 容易把一个局部目标扩大成多处联动修改

只要需要新增共享字段、调整类型含义、同步多个消费方，本轮就该停下。

---

### 4. `src/app/api/chat/route.ts`

默认别碰原因：

- API 行为变更影响主交互链路
- 可能牵涉 mock / 真实模型模式的兼容关系
- 不是脏工作区里适合随手推进的区域

---

## 五、最短落点判断法

当你已经决定“这轮继续做一点”，但还没想好落在哪个文件时，可以按下面顺序：

1. 能否只交付 `docs/` 下的独立成果？
   - 能：优先做
   - 不能：继续下一题

2. 能否只改一个组件文件中的提示语、空态、辅助说明或 aria 标签？
   - 能：继续评估
   - 不能：暂停

3. 是否会碰 `page.tsx`、`memory.ts`、`types/index.ts`、`api/chat/route.ts`？
   - 会：默认暂停
   - 不会：继续评估

4. 改完后能否只靠最小人工检查 + `npm run build` / `npm run lint` 完成复验？
   - 能：可以进入本轮候选
   - 不能：不适合当前回合

## 六、推荐的一句话记录模板

### 如果本轮选的是文档触点
- 本轮继续避免扩大业务代码冲突面，选择新增一份独立文档，把 {{抽象原则}} 落到 {{更具体的判断或落点}}。

### 如果本轮选的是组件触点
- 本轮仅调整 `{{文件名}}` 中的 {{提示语 / 空态 / aria / 说明文案}}，不触碰共享类型、持久化结构或主状态机。

### 如果本轮必须停下
- 候选改动已进入 {{共享类型 / 恢复逻辑 / 主状态机 / 多方案取舍}} 区域，超出当前低风险自动迭代边界，需先人工权衡。

## 七、一句话结论

当 LifeScript 当前工作区已经较脏而工程验证仍通过时，继续积极推进的关键不是“还能不能改”，而是**能否先落在边界更清楚的触点上**：优先 `docs/`，其次单组件说明性增强，最后明确避开状态机、持久化、共享类型与 API 核心行为。
