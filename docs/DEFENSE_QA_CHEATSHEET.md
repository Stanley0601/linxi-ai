# LifeScript Defense Q&A Cheatsheet

面向比赛答辩、现场问答、临时追问时的速答卡。

当 `npm run build` 与 `npm run lint` 已通过，但工作区较脏、不适合继续扩大业务代码改动时，这类独立答辩辅助文档是更稳妥的自动迭代交付物。

## 适用场景

- 比赛答辩前最后 5 分钟快速过稿
- 录屏配音时需要更顺的讲法
- 现场被追问“为什么这样设计”时快速组织回答
- 协作者接手演示时，需要统一口径

---

## 1. 一句话产品定义

可优先使用：

> LifeScript 不是“你问一句、AI 回一句”的工具，而是一个真的在 QQ 里活着、会主动联系你、会发动态、会被关系影响人生走向的 AI 好友。

更短版本：

> 我们想做的不是聊天机器人，而是会和你一起生活的 AI 好友。

---

## 2. 评委最可能追问的 8 个问题

### Q1：你们和普通 AI 聊天产品最大的区别是什么？

建议回答：

> 普通 AI 大多是被动响应式产品，用户不说话，它就不存在；而 LifeScript 里的角色会主动找你、会发动态、会随着关系推进产生不同状态。用户不是在“调用一个工具”，而是在和一个持续生活着的 AI 建立关系。

可补一句：

> 我们把“对话”扩展成了“关系 + 状态 + 时间线”。

### Q2：为什么要做成 QQ 场景，而不是独立聊天窗口？

建议回答：

> QQ 本身就是熟人社交和长期关系最容易成立的场景。放在 QQ 语境里，主动消息、空间动态、关系升温、结局收束都会更自然，用户也更容易把它理解成“一个活着的好友”，而不是一个纯工具型助手。

### Q3：这个产品最核心的创新点是什么？

建议回答：

> 核心创新点不是某一个单独功能，而是把主动消息、关系阶段、空间动态、人生结局放进同一条体验链路里，让 AI 从“单轮回答者”变成“持续存在的关系对象”。

### Q4：用户的每句话具体会影响什么？

建议回答：

> 用户的话会影响角色的关系状态、剧情推进、动态内容和最终结局。也就是说，用户输入不是只影响当下这条回复，而是在影响这个 AI 的后续人生轨迹。

### Q5：如果没有真实模型，项目是不是就跑不起来？

建议回答：

> 不会。我们做了本地剧情和兜底链路，确保在没有模型密钥或现场网络不稳定时，核心产品流程依然可以完整演示。这样既保证稳定性，也方便快速验证产品体验。

### Q6：为什么你们强调“主动消息”而不是只做聊天质量？

建议回答：

> 因为“主动”决定了用户会不会把它当成一个活着的好友。聊天质量很重要，但如果它永远只在被调用时出现，用户很难产生牵挂感。主动联系、关系推进和空间暴露，才是这个产品差异化最强的部分。

### Q7：这个项目的工程完成度体现在哪里？

建议回答：

> 工程上我们已经完成了稳定的前端原型、聊天接口、状态持久化、关系阶段系统、动态筛选与演示恢复链路，并且可以通过 lint、typecheck、build 与 CI 做基础验收。它不是静态稿，而是可以运行、可以验证、可以迭代的产品原型。

### Q8：如果继续迭代，下一步最值得做什么？

建议回答：

> 下一步最值得投入的是更细的剧情分支、多结局策略、长期记忆机制，以及更强的主动触达策略。现在的重点已经不是“能不能跑起来”，而是让 AI 的人生轨迹更丰富、关系变化更真实。

## 3. 可直接套用的答辩结构

如果只给你 60~90 秒介绍产品，可按下面顺序：

1. **先定义问题**：现在很多 AI 更像一次性工具，不像真正的社交关系对象
2. **再讲方案**：LifeScript 让 AI 在 QQ 里像好友一样主动生活
3. **再讲体验链路**：主动消息 → 聊天推进 → 空间动态 → 关系变化 → 结局收束
4. **最后讲价值**：用户感受到的不是“回答得对”，而是“这个 AI 真的在和我一起生活”

可直接说：

> 我们不是在优化一轮问答，而是在设计一段会持续推进的人机关系。

## 4. 工程亮点速答

如果评委更关注实现，可以优先提这几项：

- 基于 **Next.js 16 + React 19 + TypeScript** 的可运行原型
- 聊天接口支持 **Mock / 真实模型** 双模式
- 本地状态持久化，方便恢复演示现场
- 关系阶段、兴趣画像、天气关怀、动态筛选已形成联动
- 工程已可执行 `npm run lint`、`npm run typecheck`、`npm run build`
- 已补充 CI，方便 push / PR 基础验收

推荐一句话：

> 我们既考虑了产品叙事，也考虑了现场演示和持续迭代的工程稳定性。

## 5. 风险追问时的稳妥回答

### 如果被问：这是不是太依赖 Demo 叙事？

建议回答：

> 我们承认当前阶段首先要把核心体验链路打磨清楚，所以会优先保证主动消息、关系推进和空间内容这条主线的完整性。但工程上我们已经把状态持久化、恢复机制和验证链路搭起来，具备继续扩展的基础。

### 如果被问：会不会只是预设剧情，不够智能？

建议回答：

> 当前阶段我们有意让“可控体验”和“可演示稳定性”优先，这并不排斥后续接入更强模型。相反，先把人生阶段、关系推进和空间表达这些产品骨架打稳，后续模型升级才更有价值承接点。

### 如果被问：为什么没有直接做线上发布？

建议回答：

> 比赛冲刺期我们优先把本地可运行、可验证、可录屏的原型打磨稳定，这样更利于快速迭代与现场展示；后续部署到 Vercel 这类平台已经具备明确路径。

## 6. 最容易讲顺的三个亮点组合

### 组合 A：最稳妥

- 主动消息
- 关系推进
- 结局收束

适合时间短、只想保主线时使用。

### 组合 B：最有“活着感”

- 主动消息
- 空间动态
- 用户影响人生走向

适合强调“AI 在生活”的产品感。

### 组合 C：最偏工程完成度

- 本地可运行原型
- 状态持久化与演示恢复
- lint / build / CI 验证

适合面对偏技术评委时使用。

## 7. 答辩时尽量避免的表达

不太建议直接说：

- “我们就是做了一个陪聊 AI”
- “这个主要靠 Prompt 先撑起来”
- “暂时很多都是写死的”
- “现在只是一个页面 Demo”

更建议改成：

- “我们在验证 AI 好友的长期关系体验”
- “当前阶段优先把可讲述、可验证的体验链路打稳”
- “我们先把产品骨架和状态机制沉淀下来，再继续增强模型能力”
- “这已经是可运行、可验证、可继续迭代的原型”
