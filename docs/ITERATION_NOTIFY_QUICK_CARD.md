# LifeScript Iteration Notify Quick Card

用于在每轮积极型自动迭代结束时，30 秒内快速整理出一条“可以立刻发出去”的结果通知。

它不替代详细日志，也不替代长篇说明文档，而是专门解决一个很实际的问题：

> 当你已经完成检查、改动或停手判断后，怎样用最短时间把结果说明白，并确保没有漏掉关键字段？

---

## 1. 什么时候优先看这张速卡

适用于以下场景：

- 已完成 `git status --short --branch`
- 已执行 `npm run build` 与 `npm run lint`
- 已完成一项低风险改动，或已决定本轮暂停
- 需要把结果主动同步给自己、协作者，或作为下一轮接手输入
- 不想每次通知都临时组织措辞，导致遗漏风险说明或后续建议

一句话原则：

> 通知要追求的不是“写得长”，而是“让对方 10 秒内知道本轮做了什么、现在是否安全、接下来该怎么办”。

---

## 2. 30 秒通知骨架

如果时间很紧，直接按下面顺序填空：

```markdown
### 本轮自动迭代结果
- 分支：`{branch}`
- Git 状态概览：{git_summary}
- 本轮目标：{goal}
- 当前结果：{result}
- 验证结果：`npm run build` {build_result}；`npm run lint` {lint_result}
- 风险说明：{risk_note}
- 后续建议：{next_step}
```

这 7 项里，最容易遗漏的是：

- 当前结果到底是成功 / 异常 / 主动暂停
- 风险说明里有没有明确写“本轮没碰什么”
- 后续建议里有没有明确写“现在该继续还是先停”

---

## 3. 三种结果的最短写法

### A. 成功完成

```text
已完成一轮积极型自动迭代；本轮完成 {change_summary}，build/lint 均通过，未触碰 {unsafe_area}，建议下一轮继续优先选择独立、低冲突的小交付。
```

### B. 异常结束

```text
本轮在 {failure_step} 遇到异常，已停止继续扩大改动；当前 build/lint 结果为 {verification_summary}，建议先单独收敛异常点，再决定是否继续自动迭代。
```

### C. 主动暂停

```text
本轮已完成固定检查，但因 {pause_reason} 主动暂停继续改动；当前 build/lint 结果为 {verification_summary}，建议先人工确认边界或方案后再继续。
```

---

## 4. 推荐直接复用的句子

### Git 状态概览

可直接选一句再微调：

- 当前分支正确，但工作区已存在较多未提交业务与文档改动，本轮继续避免扩大冲突面
- 当前分支正确，工作区存在少量未提交改动，仍适合做独立、单点、可复验的低风险交付
- 当前分支与远端跟踪关系正常，但工作区较脏，默认不进入跨文件或跨模块修改

### 风险说明

可直接选一句再微调：

- 本轮仅新增独立文档与索引入口，未触碰核心页面、共享类型、状态机或恢复逻辑
- 本轮仅处理单个明确问题，未顺手扩大到重构、跨页联动或数据结构调整
- 本轮未继续推进代码改动，主动避免误伤现有未提交业务修改边界

### 后续建议

可直接选一句再微调：

- 若下一轮仍处于当前较脏工作区，优先继续做独立文档、自检卡或单文件微增强
- 若下一步需要触碰共享类型、恢复逻辑或主状态机，应先停下并做人工权衡
- 若要继续推进体验优化，优先选择收益明确、单文件、可立即复验的小改动

## 5. 三个常见漏项提醒

### 漏项 1：只说“完成了”，没说验证情况

不推荐：

```text
本轮已完成文档补充，建议后续继续推进。
```

更稳妥：

```text
本轮已完成文档补充，`npm run build` 与 `npm run lint` 均通过，建议后续继续优先选择独立、低冲突的小交付。
```

### 漏项 2：只说“暂停”，没说为什么暂停

不推荐：

```text
本轮先暂停。
```

更稳妥：

```text
本轮因下一步会触碰多文件与现有未提交业务改动边界，已主动暂停继续扩改，避免放大冲突面。
```

### 漏项 3：只说“有风险”，没说风险边界

不推荐：

```text
本轮风险可控。
```

更稳妥：

```text
本轮仅新增独立文档，未触碰核心页面、共享类型、状态机或恢复逻辑，冲突与回归风险低。
```

---

## 6. 发出前最后 10 秒检查

发通知前，只看这 5 个问题：

- [ ] 分支写了吗？
- [ ] 当前结果写清是成功 / 异常 / 暂停了吗？
- [ ] build / lint 结果写了吗？
- [ ] 本轮没碰什么高风险区域写了吗？
- [ ] 后续建议写了吗？

如果其中有两项没写，这条通知通常还不够稳。

---

## 7. 与其他文档的分工

- `docs/ITERATION_NOTIFICATION_TEMPLATE.md`：适合需要完整字段、标准表达的结果通知
- `docs/ITERATION_NOTIFY_PLAYBOOK.md`：适合理解为什么无论成功、异常还是暂停都必须通知
- `docs/ITERATION_WRAPUP_CARD.md`：适合每轮最后 3 分钟的整体收尾动作
- **本文件**：适合在通知动作本身上快速落地，减少“知道该通知，但临时不会写”的摩擦

---

## 8. 一句话结论

在 LifeScript 当前阶段，一条短而完整的结果通知，本身就是自动迭代闭环里最容易被忽略、但最能提升协作质量的一步。
