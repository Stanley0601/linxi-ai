# LifeScript Safe Single-File UI Enhancements

用于在 `build` / `lint` 已通过、但工作区已经较脏时，进一步把“还能继续做一点什么”收敛到**单文件、说明性、可快速复验**的 UI 微增强范围。

它和已有文档的分工如下：

- `docs/LOW_RISK_CHANGE_CATALOG.md`：回答“哪类改动通常更稳妥”
- `docs/LIFESCRIPT_LOW_RISK_BACKLOG.md`：回答“当前项目还有哪些值得做的低风险候选项”
- `docs/LIFESCRIPT_SAFE_TOUCHPOINT_MAP.md`：回答“如果要落到文件，优先看哪里、默认别碰哪里”
- **本文**：回答“当你准备继续做代码改动时，哪些**单文件 UI 微增强**通常更安全、如何判断值得做、做到哪一层就该停”

一句话目标：

> 当继续改代码仍有价值，但工作区又不适合扩展到多文件联动时，帮助后续自动迭代优先选择单文件、低争议、收益可解释的 UI 微增强。

---

## 1. 使用前提

建议仅在以下条件同时成立时使用：

- 已执行 `git status --short --branch`
- 已确认当前分支是预期分支
- 已执行 `npm run build`
- 已执行 `npm run lint`
- 当前没有必须优先修复的明确工程报错
- 你已经判断“本轮继续做一点代码改动”比继续补文档更合适

如果 `build` 或 `lint` 还未通过，先修第一个明确问题；如果你还不能确定是否该继续改代码，先看 `docs/SAFE_CHANGE_DECISION_TREE.md`。

---

## 2. 什么叫“单文件 UI 微增强”

本文默认指下面这类动作：

- 只修改一个组件文件
- 以提示语、空态、辅助说明、标签、可访问性或轻量展示增强为主
- 不新增共享类型
- 不调整本地持久化结构
- 不修改主状态机、核心排序或恢复逻辑
- 改完后可以通过最小人工检查 + `build` / `lint` 快速复验

一句话判断：

> 这类改动的价值通常来自“让已有能力更容易被理解、被演示、被感知”，而不是“重新定义能力本身”。

---

## 3. 最适合优先考虑的增强类型

### A. 提示语更具体

适合：

- 解释当前筛选、当前状态、当前能力为什么存在
- 让用户知道下一步该做什么
- 让录屏或答辩时的讲述成本更低

示例方向：

- 把“暂无内容”改成“为什么暂无内容 + 现在可以做什么”
- 把“继续上次演示”解释得更明确
- 把建议回复、快捷操作、恢复默认等入口说得更容易理解

### B. 空态更可讲述

适合：

- 当前页面在数据较少时显得突兀
- 演示时空白状态不好解释
- 用户第一次进入某页时不容易知道页面价值

示例方向：

- 空态标题补一句背景解释
- 空态说明增加推荐下一步
- 空态文案更贴近产品价值而不是调试口吻

### C. 轻量辅助说明

适合：

- 页面已有数据，但“为什么值得看”表达不够清楚
- 某个统计或标签存在，但讲述成本较高
- 需要帮助观众把展示层理解成产品能力，而不是演示数据

示例方向：

- 给状态摘要补一句解释
- 给统计卡片补一句用途说明
- 给分组或模块标题补一句更清楚的上下文

### D. 无障碍或语义补充

适合：

- 已有交互缺少更清楚的语义标签
- 视觉上能看懂，但读屏或键盘用户不够友好
- 同时还能提升代码可解释性

示例方向：

- 为按钮、输入区、列表区补 aria 标签
- 优化 heading 层级与辅助描述
- 为状态图标补充语义说明

## 4. LifeScript 当前更适合看的文件

### `src/components/MessageListPage.tsx`

优先考虑：

- 搜索为空时的引导语
- 当前筛选 / 当前排序的轻量提示
- 快捷键提示的解释性文案
- 固定、静音、未读等状态的无障碍描述

默认别碰：

- 搜索命中逻辑
- 排序评分机制
- 与本地持久化绑定的筛选结构

- 建议回复的辅助说明
- 首轮开场引导的微文案
- 局部 aria 标签补充

默认别碰：

- 聊天推进状态
- 主动消息链路
- 与生成逻辑强耦合的行为修改

### `src/components/MomentsFeed.tsx`

优先考虑：

- 当前模式的解释性文案
- 恢复默认入口的说明
- 空态说明增强
- 演示时可直接复用的微提示

默认别碰：

- 动态排序规则
- 点赞 / 评论持久化逻辑
- 跨页面共享记忆逻辑

### `src/components/MyProfileTab.tsx`

优先考虑：

- 本地数据摘要说明
- “继续上次演示”入口的辅助解释
- 画像、偏好、统计卡片的讲解性补充

默认别碰：

- 恢复入口逻辑
- 缓存结构
- 依赖多个来源的大型统计新增

### `src/components/EndingView.tsx` / `src/components/TimelineView.tsx`

优先考虑：

- 总结卡片的解释语
- 阶段说明语
- 标题层级与辅助文案
- 更适合演示收束的结尾提示

默认别碰：

- 结局判定逻辑
- 时间线数据模型
- 与指标计算相关的结构变化

## 5. 三步快速判断：这项改动值不值得做

### 第一步：收益能否一句话说清

可以继续的典型写法：

- 优化某页面空态说明，让首次演示时更容易解释下一步操作
- 给已有统计卡片补充用途说明，降低答辩时的讲述成本
- 为某组快捷操作补充语义标签，提升可访问性与可解释性

如果你只能说“看起来会更顺一点”，通常还不够。

### 第二步：能否限制在单文件内完成

如果改着改着需要：

- 新增共享字段
- 调整多个组件协作方式
- 修改顶层页面状态
- 联动本地存储或恢复逻辑

说明这项改动已经不再适合当前回合。

### 第三步：改完后能否快速复验

至少应该能做到：

- 明确说出最小人工检查点
- 跑完 `npm run build`
- 跑完 `npm run lint`

如果复验都说不清，通常说明目标边界还不够稳。

---

## 6. 什么时候应该停下，不再继续顺手扩改

命中任一条就建议停止继续：

- 本轮已经完成一项独立、低风险、可解释的交付
- 下一步开始碰第二个文件
- 下一步需要新增字段或联动多个页面
- 下一步收益已经说不清
- 你只是因为“还可以再顺手做一点”而想继续改

一句话原则：

> 单文件 UI 微增强之所以安全，不是因为它“看起来很小”，而是因为它始终有明确边界；一旦边界开始外溢，就该停下。

---

## 7. 推荐记录模板

```markdown
- 本轮继续避免扩大核心业务改动范围
- 在 `build` / `lint` 通过的前提下，选择一项单文件 UI 微增强
- 仅修改 `{{file}}` 中的 {{提示语 / 空态 / 辅助说明 / aria 标签 / 轻量展示文案}}
- 未触碰共享类型、持久化结构、主状态机或 API 核心逻辑
- 完成后再次执行 `npm run build` 与 `npm run lint`
```

---

## 8. 一句话结论

当 LifeScript 当前工作区已经较脏、但你又确认还有必要继续做一点代码改动时，最稳妥的推进方式通常不是扩大到多文件联动，而是优先选择**收益明确、边界清楚、可快速复验的单文件 UI 微增强**。
