# LifeScript 本地电脑休眠迭代风险速卡

用于回答一个在本地个人电脑执行自动迭代时很容易被忽略、但又非常现实的问题：

> 如果这一轮自动迭代跑在本地 Mac 上，而电脑进入了休眠、锁屏、磁盘卸载或网络短暂断开，该怎么看待这轮结果、下一步先做什么？

它不是为了替代 `docs/ITERATION_RESUME_PROTOCOL.md`、`docs/ITERATION_NOTIFY_PLAYBOOK.md` 或 `docs/WORKSPACE_DIRTY_ITERATION_PLAYBOOK.md`，而是把**本地设备特有的中断风险**单独拎出来，帮助后续每一轮更快判断：

- 这次中断是不是代码问题
- 是否还能继续信任本轮验证结论
- 恢复后第一步应该做什么
- 什么时候必须停止继续扩改并主动同步

---

## 1. 什么时候该看这份速卡

适用于下面这些本地场景：

- 自动迭代运行在个人 Mac 上，而不是持续在线的服务器环境
- 电脑在任务期间进入休眠、合盖、锁屏后恢复
- 外接磁盘、同步盘或项目目录所在卷一度不可用
- 网络一度断开，恢复后不确定 build / lint 结果是否仍可信
- 本轮执行结果显示“目录找不到”“命令中断”“进程消失”或类似异常

一句话判断：

> 只要这一轮依赖的是“本地机器持续在线”，就要默认考虑休眠与设备状态变化带来的中断风险。

---

## 2. 先区分：这是不是代码问题

本地中断最容易误判的地方，是把“机器状态问题”误当成“仓库代码问题”。

### 更像设备 / 环境信号

通常包括：

- 项目目录暂时找不到
- 之前还在运行的命令突然中断
- 恢复后终端进程已不存在
- 网络相关请求在恢复前后表现不一致
- 本轮没有形成明确的代码报错栈，而是直接被打断

### 更像代码 / 工程信号

通常包括：

- `npm run build` 出现稳定可复现的编译错误
- `npm run lint` 出现稳定可复现的规则报错
- 同一问题在重新执行后依然出现
- 错误明确指向某个文件、类型、导入或语法问题

一句话原则：

> 如果异常发生在“机器恢复前后”，先怀疑环境连续性，而不是先扩大代码修复范围。

---

## 3. 本地休眠后，哪些结论默认不该直接沿用

命中下面任一情况，本轮旧结论都不应直接照搬：

- build 还没跑完电脑就休眠了
- lint 还没跑完进程就消失了
- Git 状态是在恢复前检查的，而恢复后目录或挂载状态已经变化
- 项目目录曾短暂不可用
- 恢复后你已经说不清“当前终端里的结果”到底对应休眠前还是休眠后

这时最稳妥的动作不是猜，而是把以下步骤重新执行一遍：

1. 重新确认项目目录可访问
2. 重新确认当前分支与 Git 状态
3. 重新执行 `npm run build`
4. 重新执行 `npm run lint`
5. 再决定继续补文档、做单文件微增强，还是主动暂停

---

## 4. 恢复后的推荐顺序

建议把“从休眠恢复”视为一次小型重启，而不是直接接着上一轮惯性继续改。

```text
确认机器已恢复稳定
  → 确认项目目录可访问
  → 重新检查 git status / 当前分支
  → 重新跑 build
  → 重新跑 lint
  → 回看上一轮目标是否仍成立
  → 再决定继续推进还是暂停
```

### 最短恢复动作

- 先确认 `/Users/stanleyyou/lifescript` 仍可访问
- 再确认当前仍在预期分支
- 再确认本轮之前看到的未提交改动仍然存在且没有异常变化
- 重新跑验证命令，不直接复用旧结果
- 若本轮原本就已接近边界，优先选择停下并同步，而不是继续扩改

---

## 5. 哪些情况恢复后仍适合继续低风险推进

满足下面条件时，通常还可以继续：

- 项目目录恢复正常可访问
- 当前分支仍是预期分支
- `git status --short --branch` 结果与休眠前没有出现不可解释的异常变化
- `npm run build` 重新执行通过
- `npm run lint` 重新执行通过
- 本轮目标仍是单点、低冲突、无需主观权衡的目标

这时仍建议优先：

- 独立文档补丁
- 单文件文案 / 空态 / aria 增强
- 已有能力的说明性展示增强

---

## 6. 哪些情况恢复后更应该直接停下

命中任一条，建议停止继续扩改并主动同步：

- 项目目录恢复后仍不可访问
- Git 状态与休眠前相比出现难以解释的变化
- build / lint 重新执行后失败
- 本轮下一步已经需要跨多个文件或多个方案取舍
- 你已经无法确认当前未提交改动哪些是原有的、哪些是本轮新增的

一句话原则：

> 休眠后的不确定性如果已经叠加到“代码边界也说不清”，就不应继续自动扩改。

---

## 7. 通知里建议明确写什么

如果本轮受本地休眠或设备状态变化影响，通知里建议显式写清：

- 本轮是否发生了本地设备中断
- 中断后是否已重新检查项目目录与 Git 状态
- build / lint 是否为恢复后重新执行的结果
- 当前是否已停止继续扩大改动
- 下一步建议是“继续低风险推进”还是“等待人工处理”

推荐写法示例：

```markdown
- 当前结果：本轮执行受本地设备休眠影响，已停止沿用休眠前结论
- 已复核：项目目录可访问；当前分支与 Git 状态已重新检查
- 验证结果：`npm run build` ✅；`npm run lint` ✅（均为恢复后重新执行）
- 风险说明：本轮未继续扩大到需要多方案权衡的改动，仍维持低风险边界
```

如果恢复后仍失败，也应直接说明失败点，而不是只写“本轮未完成”。

---

## 8. 与其他文档的分工

- `docs/ITERATION_RESUME_PROTOCOL.md`：回答“新一轮开始时如何从上一轮结果安全恢复”
- `docs/WORKSPACE_DIRTY_ITERATION_PLAYBOOK.md`：回答“工作区较脏但验证通过时还能安全做什么”
- `docs/ITERATION_NOTIFY_PLAYBOOK.md`：回答“成功、异常、暂停三种结果都必须主动通知”
- **本文**：回答“如果本地电脑休眠、目录短暂不可用或设备状态变化，中断后的判断顺序和复核动作是什么”

---

## 9. 一句话结论

在本地个人电脑上做自动迭代时，休眠和设备状态变化本身就是执行环境的一部分；一旦发生中断，最稳妥的做法不是沿用旧结论继续改，而是把目录、Git 与验证结果重新复核后再决定是否继续。
