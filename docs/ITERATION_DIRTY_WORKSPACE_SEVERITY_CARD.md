# LifeScript Dirty Workspace Severity Card

用于在 `git status --short --branch` 已显示工作区不干净、但 `build` 与 `lint` 已通过时，进一步判断当前到底是**轻度脏 / 中度脏 / 高风险脏**，并把“还能安全做什么”快速收敛成一句可执行结论。

它不是替代 Git 基础知识，而是给自动迭代时的现实问题一个更快的答案：

> 现在这个工作区，究竟还能继续补什么，还是应该直接停手。

---

## 1. 什么时候该看这份速卡

适用于以下场景：

- 已执行 `git status --short --branch`
- 已确认当前分支正确
- `npm run build` 已通过
- `npm run lint` 已通过
- 你还想继续做一轮积极型自动迭代，但担心继续扩改会误伤现有修改

一句话前提：

> 这份文档只回答“工作区有改动但工程已通过时，还能安全推进到哪一层”。

如果 `build` 或 `lint` 失败，先回到工程分流，优先处理首个明确问题。

---

## 2. 先用 20 秒做一级分类

先看两个维度：

1. 改动数量是不是已经明显超过少量补丁
2. 改动文件里是否已经包含核心页面、共享类型、缓存/恢复逻辑、API 或样式骨架

然后直接套下面的一级判断：

### 轻度脏

常见信号：

- 改动数量少
- 主要是文档、说明、单个组件或单页微调
- 你能在 20 秒内说清每个改动大概在做什么

### 中度脏

常见信号：

- 业务文件和文档同时在改
- 组件、样式、页面已有多处并行修改
- 虽然大方向看得懂，但已经不适合继续顺手扩大改动范围

### 高风险脏

常见信号：

- 多个核心页面、共享类型、恢复逻辑、API 同时被改
- 还混有新增目录、未纳管文件或意图不清的修改
- 你无法快速判断哪些改动是一个主题，哪些只是临时试验

如果你需要超过 30 秒才能解释工作区边界，默认按**高风险脏**处理。

---

## 3. 三档脏度分别意味着什么

### A. 轻度脏：可以做同主题补充

更像：

- 一轮未收尾的小补丁
- 文档已经开了头，还能继续补完整
- 单组件微优化还没收尾

本轮可做：

- 继续补同一主题文档
- 单文件文案优化
- 单组件无障碍补充
- 极小范围体验修正

本轮不要做：

- 借机扩到多个页面
- 顺手改共享类型
- 从一个微调演变成结构调整

一句话结论：

> 轻度脏不等于能随便继续改，而是只适合把原本已经很接近完成的低风险动作补完整。

### B. 中度脏：优先独立交付，不再扩大业务改动面

更像：

- 工作区已经有不少业务与文档混合修改
- 当前工程虽然通过，但继续改代码的交叉面会明显变大
- 再往前一步就很可能从“继续推进”变成“开始碰边界”

本轮优先做：

- 新增独立文档
- 补日志、检查卡、通知模板、交接说明
- 做零代码闭环
- 最多只做边界极清晰的单点文案补充

本轮默认不做：

- 继续改多个组件
- 调整页面间联动行为
- 修改本地持久化或恢复逻辑
- 小功能继续外扩

一句话结论：

> 中度脏时，最专业的积极推进通常不是“再补一段代码”，而是“再交付一份低冲突成果”。

### C. 高风险脏：默认停止继续扩改

更像：

- 已经进入“很多地方都动了，但边界不够清楚”的状态
- 继续推进前，需要先判断现有改动哪些该保留、哪些该回滚、哪些属于哪个目标
- 工程通过并不能证明继续扩改仍然安全

本轮建议：

- 不再新增代码改动
- 如果需要，可只补一条记录或一份说明文档
- 主动通知当前边界与暂停原因
- 把下一步收敛成待人工判断的问题

一句话结论：

> 高风险脏时，继续自动扩改通常不是积极，而是把模糊边界继续放大。

---

## 4. 看到哪些文件时要自动提高风险判断

出现以下任意一类信号，都应该把脏度至少上调半级：

- `src/app/page.tsx`
- `src/types/index.ts`
- `src/lib/memory.ts`
- `src/app/api/chat/route.ts`
- `src/app/layout.tsx`
- `src/app/globals.css`
- 多个核心页面组件同时修改
- `docs/` 之外还有大量业务文件改动
- 存在新增目录但还未确认用途

原因不是这些文件“不能改”，而是它们往往意味着：

- 影响范围更大
- 与其他未提交改动交叉概率更高
- 需要更多上下文才能安全继续推进

---

## 5. 一条最实用的判断规则

如果同时满足下面 3 条，默认不要继续扩改业务代码：

- `build` 已通过
- `lint` 已通过
- `git status --short --branch` 显示多个业务文件 + 核心文件 + 文档并行修改

这时更推荐：

1. 补一份独立文档或记录
2. 更新迭代日志
3. 主动通知本轮结果
4. 停止继续扩大改动面

---

## 6. 最短落地模板

### 轻度脏可复用写法

```text
当前分支正确，工作区为轻度脏；本轮仍可在同一主题内补完低风险独立改动，但不继续扩到多个业务模块。
```

### 中度脏可复用写法

```text
当前分支正确，工作区已有较多业务与文档并行改动；build 与 lint 虽已通过，但本轮继续限制在独立文档或零代码闭环范围内。
```

### 高风险脏可复用写法

```text
当前分支正确，但工作区核心改动已较多且边界不够清晰；继续推进需要先判断现有修改的保留策略，因此本轮应主动停手并说明。
```

---

## 7. 和其他文档怎么配合

推荐组合顺序：

1. `docs/ITERATION_GIT_STATUS_SIGNAL_CARD.md`
   - 先判断分支是否正确、工作区是否脏
2. `docs/ITERATION_DIRTY_WORKSPACE_SEVERITY_CARD.md`
   - 再判断脏到哪一层、还能安全推进什么
3. `docs/WORKSPACE_DIRTY_ITERATION_PLAYBOOK.md`
   - 最后决定该补文档、做微优化还是直接停手

如果本轮已经结束，还应配合：

- `docs/ITERATION_WRAPUP_CARD.md`
- `docs/ITERATION_NOTIFICATION_TEMPLATE.md`
- `docs/ITERATION_NOTIFY_PLAYBOOK.md`

---

## 8. 一句话结论

当工作区已经不干净、而工程验证又通过时，真正重要的不是“还能不能继续做事”，而是“还能在多大边界内继续做对的事”。
