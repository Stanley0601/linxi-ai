# LifeScript Iteration Git Status Signal Card

用于在每轮积极型自动迭代开始前，把 `git status --short --branch` 与 `git branch --show-current` 的原始输出，快速翻译成“现在还能安全做什么”的行动结论。

这份卡片的重点不是教你怎么看 Git 基础命令，而是帮助你在 LifeScript 当前这种**工作区可能较脏、但仍想低风险推进**的阶段，更稳定地完成三件事：

1. 判断当前是否还在目标分支
2. 判断当前工作区到底脏到什么程度
3. 把原始输出整理成可直接写进日志或通知的一句话摘要

---

## 1. 什么时候该看这份卡片

适用于以下场景：

- 正准备开始一轮积极型自动迭代
- 已执行 `git status --short --branch`
- 已执行 `git branch --show-current`
- 想快速判断本轮更适合修工程问题、补文档、做微优化，还是应该先停下
- 想把 Git 原始输出整理成稳定、低歧义的记录或通知文本

一句话原则：

> `git status` 不是走流程的截图动作，而是决定本轮风险边界的第一道分流。

---

## 2. 每轮最少要先跑哪两个命令

```bash
git status --short --branch
git branch --show-current
```

推荐先看这两个命令，再决定是否继续执行：

```bash
npm run build
npm run lint
```

原因很简单：

- 分支不对，说明本轮起点就不安全
- 工作区状态不清，说明你还不知道是否会误伤现有改动
- `build` / `lint` 没跑，说明你还不知道当前是“该先修错”还是“可以选低风险增量”

---

## 3. 先看分支：不在目标分支就不要继续扩改

在 LifeScript 当前基线下，优先确认：

- 当前分支是否仍为 `feat/v12-unified-baseline`
- 是否出现了你并不打算在本轮操作的临时分支
- 是否存在 detached HEAD 或无法快速说明来源的分支状态

### 可以继续的信号

- 当前分支就是目标基线分支
- 分支名称和预期一致
- 没有出现需要先做分支策略判断的情况

### 应暂停的信号

- 当前分支不是预期分支
- 你无法判断为什么会在这个分支上
- 下一步需要先做 rebase、merge 或分支切换取舍

一句话判断：

> 分支不明确时，最正确的动作不是继续改，而是先停下说明。

---

## 4. 再看工作区：把状态分成 4 档

### A. 干净工作区

典型信号：

- `git status --short --branch` 没有列出文件改动
- 只有分支信息，没有新增、修改、删除文件

本轮建议：

- 如果 `build` / `lint` 失败，先修首个明确工程问题
- 如果 `build` / `lint` 通过，可考虑单点体验优化、小功能增强或轻度重构

### B. 轻度脏：只有少量独立文件改动

典型信号：

- 只有 1~3 个文件改动
- 主要集中在文档、说明文件或单一组件
- 没有多个核心页面同时变更

本轮建议：

- 优先继续做同一主题下的独立补充
- 可以做单文件微优化
- 避免顺手扩散到多个业务模块

### C. 中度脏：业务文件与文档并行改动

典型信号：

- `src/app/page.tsx`、多个组件、样式、类型、文档同时存在修改
- 你能看懂这些改动大概在做什么，但交叉面已经不小
- 本轮如果再碰核心页面，冲突面明显会上升

本轮建议：

- 若 `build` / `lint` 失败，先只修首个明确工程问题
- 若 `build` / `lint` 通过，优先交付独立文档、单点文案优化或零代码闭环
- 默认不继续扩大核心业务改动面

### D. 高风险脏：多处核心结构同时改动，且边界说不清

典型信号：

- 多个核心页面、共享类型、API、样式、恢复逻辑同时改动
- 还有新增目录、未纳管文件、历史意图不清的改动混在一起
- 你无法在 30 秒内解释“这些改动分别属于什么目标”

本轮建议：

- 不继续自动扩张
- 若 `build` / `lint` 未通过，只修第一个明确阻塞项
- 若已经通过，优先以记录、说明、通知或文档补充收尾
- 如果下一步需要权衡哪些改动该保留、该回滚，必须暂停并说明

---

## 5. 看状态时重点盯哪几类文件

### 相对安全的信号

- `docs/`
- `README.md`
- 独立说明文件
- 单个非核心组件文件

这些通常意味着：

- 更适合继续做文档完善
- 或做边界非常清楚的微小体验优化

### 需要提高警惕的信号

- `src/app/page.tsx`
- `src/types/index.ts`
- `src/lib/memory.ts`
- `src/app/api/chat/route.ts`
- 多个页面组件同时修改

这些通常意味着：

- 当前工作区已经不是“随手继续改一点”的状态
- 本轮应更谨慎地限制目标
- 如果没有非常明确的低风险修复点，就更适合选文档或零代码闭环

## 6. 怎么把原始 Git 输出翻译成一句话摘要

推荐写法要同时说明三件事：

1. 分支是否正确
2. 工作区是否较脏
3. 这会如何影响本轮动作

### 推荐模板

```text
当前分支正确，工作区已有较多未提交业务与文档改动；为避免扩大冲突面，本轮继续限制在低风险独立交付范围内。
```

### 其他可直接复用的写法

#### 场景 A：工作区干净

```text
当前分支正确，工作区基本干净；若 build / lint 通过，可继续推进单点低风险增强。
```

#### 场景 B：文档为主的轻度脏工作区

```text
当前分支正确，工作区以文档与说明类改动为主；本轮适合继续补充独立文档或说明增强。
```

#### 场景 C：业务与文档混合改动

```text
当前分支正确，但工作区已存在较多未提交业务与文档改动；若工程验证已通过，本轮应继续避免扩大核心代码冲突面。
```

#### 场景 D：需要暂停

```text
当前分支虽正确，但工作区改动边界已不够清晰；继续推进需要先判断现有修改的保留策略，因此本轮应暂停并说明。
```

## 7. 三个常见误判

### 误判一：build / lint 通过，就说明可以继续放心改

不对。

正确理解是：

- 这只说明当前工程能过验证
- 不代表继续改不会误伤已有未提交改动
- 是否继续推进，仍取决于 Git 状态是否清晰

### 误判二：只要没有冲突提示，就说明工作区不危险

不对。

正确理解是：

- 冲突只是最表层风险
- 真正的风险往往是“边界不清却继续扩改”
- 尤其当多个核心文件同时在改时，最容易把低风险回合做成高风险回合

### 误判三：看完 git status 只要说一句“状态正常”就够了

不对。

正确理解是：

- 后续接手者需要知道“正常”具体指什么
- 通知与日志里必须把分支、脏度和动作边界说清楚
- 模糊表达会让下一轮仍然需要二次追问

---

## 8. 最短判断流程

```text
先看分支
  → 不对：暂停并说明
  → 对：再看工作区脏度
        → 干净：可做单点低风险增强
        → 轻度脏：可做同主题补充或单文件微优化
        → 中度脏：优先文档、文案、零代码闭环
        → 高风险脏：不再自动扩张，必要时暂停说明
```

---

## 10. 一句话结论

在积极型自动迭代里，`git status` 的价值不只是“看有没有改动”，而是帮助你决定：这一轮应该继续推进什么、不要碰什么、以及什么时候该停下说明。
