# Iteration Risk Summary Card

用于在每轮自动迭代结束前，快速把“这轮为什么能继续做 / 为什么应该停在这里 / 还剩哪些风险”整理成一段可复用的风险摘要，减少结果通知、迭代日志与协作交接时重复组织语言的成本。

---

## 适用场景

适合在以下条件下使用：

- 已完成 `git status --short --branch`
- 已确认当前分支仍是预期分支
- 已执行 `npm run build`
- 已执行 `npm run lint`
- 本轮已经形成一个独立结果，准备做通知、记录或交接
- 你想快速回答“为什么这轮只做到这里”而不是继续惯性扩改

如果当前 `build` 或 `lint` 还没通过，先处理首个明确报错，不要先写风险摘要。

---

## 这张卡解决什么问题

很多轮自动迭代并不是“不会做”，而是：

- 已经有可交付结果，但没把停手理由讲清楚
- 工作区本来就较脏，却没有把风险边界说出来
- 通知里只写了“做了什么”，没写“为什么没继续扩大范围”
- 协作者接手时看得到改动结果，却看不出本轮刻意避开的高风险区域

这张卡的目标不是放大风险感，而是帮助你在有成果时，用更短时间给出一份**可解释、可复述、可交接**的风险摘要。

---

## 推荐使用顺序

建议在每轮结束时按下面顺序快速过一遍：

1. 当前结果是否已经能独立交付？
2. 当前工作区脏度是否支持继续扩大改动范围？
3. 下一步如果继续做，是否会进入共享类型、状态机、持久化或多文件联动？
4. 这轮停在这里，是否已经足够说明价值？
5. 结果通知里是否已经把“验证结果 + 风险边界 + 后续建议”说完整？

如果第 1 题是“能独立交付”，而第 2～4 题中任意一题偏风险上升，通常就应优先收尾，而不是继续扩改。

---

## 风险摘要的四段式模板

每轮结束时，优先把风险摘要压缩成下面四段：

### 1. 当前起点
一句话说明本轮开始时的环境：

- 当前分支是否正常
- 工作区是否较脏
- build / lint 是否通过

示例：

> 当前分支正常，但工作区已有较多未提交业务与文档改动；`build` / `lint` 已通过，因此本轮适合继续做低风险独立交付，不适合扩大核心业务冲突面。

### 2. 本轮动作
一句话说明本轮实际做了什么：

- 文档完善 / 体验优化 / 小功能增强 / 轻度重构
- 最好落到一个具体交付物

示例：

> 本轮新增一份用于结果通知与协作交接时快速整理风险说明的独立速卡文档。

### 3. 停手理由
一句话说明为什么做到这里就该停：

- 再往前会进入什么风险区域
- 当前不继续做，不是因为没思路，而是因为边界不再低风险

示例：

> 若继续扩大范围，将开始进入多文档联动整理或业务代码层面的取舍判断，收益增量有限，但冲突面和主观决策成本会继续上升，因此本轮在独立成果形成后停止。

### 4. 后续建议
一句话说明下一轮最值得做什么：

- 优先继续文档补强
- 或先复核业务改动边界
- 或在需要人工权衡时暂停说明

示例：

> 下一轮若工作区仍保持当前状态，优先继续补强独立文档、通知模板或演示支持材料；若要进入业务逻辑调整，应先明确现有未提交改动的归属与边界。

## 适合直接复用的风险措辞

### 当工作区较脏，但本轮成果独立时

- 当前工作区已有较多未提交改动，本轮继续限制在低冲突、可独立交付的范围内。
- 本轮未触碰核心业务逻辑、共享类型、状态机或持久化结构，冲突与回归风险较低。
- 本轮选择在已有成果形成后停止，避免把低风险迭代继续推入多文件、多方案的权衡区。

### 当本轮只是补文档而不是改代码时

- 本轮优先补充可复用文档，而非继续进入业务代码，是因为当前验证已通过、代码工作区较脏，文档增强的收益更稳定、边界更清晰。
- 当前阶段继续补文档不是保守不作为，而是在已有业务改动背景下优先交付低争议、低冲突成果。

### 当你需要说明“为什么没继续优化更多”时

- 再继续优化将跨入需要主观取舍的方案区，不再适合自动迭代直接推进。
- 当前已完成的成果足够独立说明价值，继续扩展只会放大交叉修改范围。
- 本轮结束点的价值高于继续扩改带来的额外不确定性。

## 30 秒自检问题

在发送通知或追加迭代日志前，快速问自己：

1. 我有没有说明这轮开始时工作区是否干净？
2. 我有没有说明 build / lint 是否通过？
3. 我有没有明确写出本轮成果是什么？
4. 我有没有解释为什么现在停手更合理？
5. 我有没有给出下一轮的最小建议，而不是只说“后续可继续优化”？

如果这 5 个问题里有 2 个以上答不上来，说明风险摘要还不够清楚。

---

## 最短通知骨架

适合在需要快速同步结果时直接复用：

```text
分支正常，当前工作区已有较多未提交改动，build / lint 已通过。
本轮完成：{{具体成果}}。
风险边界：{{未触碰区域 / 为什么停手}}。
后续建议：{{下一轮最值得做什么}}。
```

---

## 适合追加到迭代日志的最短版本

```markdown
- 风险说明：当前工作区较脏，本轮仅交付独立且低冲突的 {{成果类型}}，未进入核心业务逻辑、多文件联动或需要人工权衡的区域，因此在形成独立结果后停止继续扩改。
```

---

## 一句话原则

自动迭代里的风险摘要，不是为了证明“这轮问题很多”，而是为了清楚说明：**为什么这轮已经做得够好，以及为什么现在停下比继续扩改更专业。**
