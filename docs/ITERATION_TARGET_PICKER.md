# LifeScript Iteration Target Picker

用于在自动迭代开始前，快速判断“这一轮最值得做、且风险最低的目标是什么”，避免在工作区较脏、工程已通过的情况下继续盲目扩大改动面。

---

## 使用时机

适合以下场景：

- 已经完成 `git status --short --branch`、`npm run build`、`npm run lint`
- `build` 与 `lint` 都通过了
- 当前工作区已经存在较多未提交改动
- 你仍想继续积极推进，但不希望误碰高风险区域
- 你希望先判断“做什么最值”，而不是直接开始改

如果当前工程检查尚未通过，先处理明确报错，不要使用这份文档替代工程修复顺序。

---

## 1. 先回答三个问题

### 问题一：这一轮是否必须改代码？

优先回答：

- 如果当前 `build` 或 `lint` 失败：**是**，先修明确问题
- 如果当前验证已通过：**不一定**，优先看是否能通过独立文档、文案增强或轻量体验优化达成本轮推进

一句话原则：

> 不是“能改代码就改代码”，而是“先做收益明确且冲突最低的事”。

### 问题二：当前工作区是否已经较脏？

出现以下任一情况，可视为“较脏”：

- 多个业务页面已经有未提交修改
- 共享类型、样式、API、主页面同时存在改动
- 已经出现多份新增文档与业务文件并行修改
- 你无法在 30 秒内说清每个未提交改动分别属于什么意图

如果答案是“是”，优先选择独立交付项。

### 问题三：本轮收益能否用一句话说清？

如果不能用一句话清楚描述本轮收益，例如：

- “让演示前检查更快完成”
- “让结果通知更容易复用”
- “让录屏中断时更快切换兜底路线”

那么这一轮很可能还没选对目标。

---

## 2. 目标选择优先级

当 `build` / `lint` 已通过且工作区较脏时，优先按下面顺序选择：

### 第一优先级：补文档

优先做这类内容：

- 演示说明
- 答辩表达辅助
- 自检清单
- 故障排查手册
- 协作交接卡
- 自动迭代执行说明
- 结果通知模板

适合原因：

- 独立性强
- 与现有业务逻辑冲突小
- 可以立即复用
- 收益易说明

### 第二优先级：改文案

适合内容：

- 空状态文案更清楚
- 按钮或提示更符合演示语境
- 反馈语更明确
- 无障碍标签补充

适合前提：

- 只改单点文案
- 不牵连共享类型与核心状态流
- 可以快速复验

### 第三优先级：小体验增强

适合内容：

- 基于已有数据的轻量摘要
- 不改变主路径的快捷入口
- 更适合桌面端演示的微交互
- 更利于答辩解释的展示增强

适合前提：

- 影响面清楚
- 改动文件少
- 不需要同步修改多个核心模块

### 默认不选：高冲突业务改动

以下情况本轮默认不选：

- 修改主状态机
- 改共享类型并联动多个页面
- 调整本地存储结构
- 修改恢复逻辑
- 对现有未提交业务改动进行覆盖式重构

---

## 3. 30 秒快速决策法

如果你只有半分钟做决定，可直接按下面顺序：

```text
build / lint 通过了吗？
  否 → 先修明确报错
  是 → 工作区脏吗？
        否 → 可考虑单点体验优化
        是 → 先选独立文档
```

如果还是犹豫，再继续问：

```text
这项改动会碰共享类型、状态恢复或主页面骨架吗？
  会 → 暂停
  不会 → 可以继续
```

---

## 4. 推荐目标模板

当你需要给本轮目标写一句话时，可直接套下面模板：

### 文档完善模板
- 补充一份用于 {{场景}} 的独立说明，降低 {{风险或成本}}

示例：
- 补充一份用于每轮开始前挑选低风险目标的独立说明，降低在脏工作区中误碰高风险代码的概率

### 文案优化模板
- 优化 {{页面或组件}} 的 {{空态/提示/反馈}} 文案，让 {{收益}}

示例：
- 优化消息列表空状态提示文案，让演示时的可解释性更强

### 小功能增强模板
- 基于已有 {{数据/状态}} 增加 {{轻量展示}}，帮助 {{演示或答辩收益}}

示例：
- 基于已有互动数据增加轻量摘要，帮助资料页在答辩中更快完成价值说明

---

## 5. 暂停条件

出现以下任一情况，先停下，不要继续自动扩展：

- 需要在两个以上实现方案中做取舍
- 你不确定现有未提交业务改动是否会被影响
- 修改范围开始从单文件扩大到多个核心文件
- 需要改共享类型才能完成目标
- 需要改恢复逻辑、本地存储、主状态机
- 本轮收益已经说不清，开始变成“顺手再改一点”

一句话原则：

> 自动迭代的价值不在于每轮都改代码，而在于每轮都留下一个可解释、可复验、可安全继承的结果。

---

## 6. 完成后的最低闭环

无论本轮选了什么目标，结束前至少确认：

```bash
git status --short --branch
npm run build
npm run lint
```

并记录：

- 当前分支
- 本轮目标
- 改动类型
- 验证结果
- 风险说明
- 后续建议

---

## 7. 一句话结论

当工程验证已经通过而工作区又较脏时，最好的积极型自动迭代目标，通常不是“再做一个更大的功能”，而是“再交付一个冲突更低、说明更强、下一轮更好接手的结果”。
