# LifeScript Iteration Verification Triage Card

用于在积极型自动迭代里遇到 `build`、`lint` 或补充执行 `verify` / `typecheck` 失败时，快速判断：**现在应该先修什么、修到哪一层、什么时候必须停下说明**。

它不是让你在失败状态下继续扩改，而是帮助你把“先恢复可验证状态”这件事做得更稳、更小、更容易复验。

---

## 适用时机

当你在 LifeScript 项目中完成固定检查后，出现以下任一情况时，可优先使用这张速卡：

- `npm run build` 失败
- `npm run lint` 失败
- 想进一步执行 `npm run verify` 或 `npm run typecheck`，但发现还有工程问题
- 当前工作区已经较脏，不希望借修错继续扩大冲突面
- 需要快速判断“继续修、只做最小恢复、还是先停下并通知”

---

## 1. 一句话原则

> 验证失败时，优先恢复**最小可复验状态**，而不是顺手把更多想法一起做掉。

如果修复动作开始跨到共享类型、恢复逻辑、主状态机或多方案取舍，本轮就不再适合自动继续扩改。

---

## 2. 先做 30 秒分流

先快速回答 4 个问题：

1. 报错是不是**首个明确、可定位**的问题？
2. 这次修复能否限制在**单点、低争议、可立即复验**的范围内？
3. 修复是否会碰到**共享类型、状态恢复、本地存储结构或主页面骨架**？
4. 修完后，是否能立刻再次执行对应验证命令确认结果？

如果前 2 个答案不是“是”，或后 2 个答案变成“会 / 不能”，就应优先停下说明，而不是继续自动推进。

---

## 3. 推荐处理顺序

### 情况 A：`npm run lint` 失败

优先做：

- 修第一个明确的 lint 报错
- 只改报错直接相关的代码
- 避免顺手整理无关命名、抽象或重构
- 修完立即重新跑 `npm run lint`

适合继续的信号：

- 报错集中在单文件
- 修改不改变行为语义
- 修复不需要扩散到多文件联动

默认暂停的信号：

- 为了通过 lint 需要大面积改写组件结构
- 修复会与当前未提交业务改动明显交叉
- 需要在多种代码风格方案之间做主观取舍

### 情况 B：`npm run build` 失败

优先做：

- 先看首个 TypeScript / 编译错误
- 只修最靠前、最确定的问题
- 修完立即重新跑 `npm run build`

适合继续的信号：

- 是变量声明顺序、类型遗漏、空值保护、单点导入等明确问题
- 受影响文件少，且行为边界清楚
- 修复不需要重写共享状态流

默认暂停的信号：

- 需要改共享类型并联动多个页面
- 需要重写恢复逻辑或本地存储结构
- 报错只是表象，真正根因仍不明确

### 情况 C：`npm run verify` / `npm run typecheck` 暴露额外问题

优先做：

- 先判断是否属于当前轮次必须恢复的最小验证范围
- 若 `build` 与 `lint` 已通过，但 `verify` 暴露的是更深层类型联动问题，要先看是否值得在本轮继续扩展

推荐判断：

- 如果问题是单点、低争议、可立即复验，可以继续修
- 如果问题已经进入跨文件联动、共享类型扩散或需要重新理解业务语义，本轮应先停止并说明

---

## 4. 低风险可修 vs 默认停手

### 可优先处理的低风险工程问题

- 明确的 lint 报错
- 单点类型遗漏或可选字段保护
- 变量声明顺序错误
- 导入路径或未使用变量问题
- 文案、无障碍属性、提示信息等不改变主流程的修正

### 默认应停手说明的问题

- 共享类型新增或重构后需要联动多个页面
- 本地缓存 / 恢复逻辑改写
- 主状态机调整
- 为了通过验证需要顺手做一轮结构重整
- 无法判断当前未提交业务改动哪些应该保留

---

## 5. 推荐最小闭环

遇到失败时，尽量保持这个最小闭环：

```text
git status --short --branch
  → git branch --show-current
  → npm run build / npm run lint（确定失败点）
  → 只修第一个明确问题
  → 重新执行对应验证命令
  → 如有必要，再补一次另一项验证
  → 记录结果
  → 主动通知成功 / 异常 / 暂停原因
```

关键点：

- 不要同时并行修多个方向
- 不要在失败状态下继续追加“顺手优化”
- 不要因为想一次做完而把修复范围扩大到核心逻辑

---

## 6. 必须停止并说明的信号

出现以下任一情况，本轮应停止自动继续修复，并明确说明原因：

- 需要在多个修复方案中做权衡
- 下一步会碰共享类型、恢复逻辑或主状态机
- 现有未提交改动的意图与边界不清楚
- 报错已经超出“第一个明确问题”，开始变成系统性排查
- 若继续修，会明显扩大文件改动范围

一句话判断：

> 只要修复不再是“单点、低争议、可立即复验”，就应该停下，而不是继续自动扩张。

---

## 7. 推荐结果记录骨架

```markdown
- 本轮目标：恢复验证可通过状态 / 判断是否应暂停
- 首个失败点：{first_failure}
- 本轮处理：{fix_or_stop_reason}
- 验证结果：`npm run build` {result}；`npm run lint` {result}
- 风险说明：{risk_note}
- 后续建议：{next_step}
```

---

## 8. 一句话结论

积极型自动迭代里，验证失败并不意味着要立即扩大修复范围；更高质量的做法，是先把问题收敛到**第一个明确故障**，只做**最小恢复**，并在超出低风险边界时及时停手说明。
