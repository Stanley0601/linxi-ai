# LifeScript Iteration Resume Protocol

用于在一轮自动迭代结束后，进一步回答一个很具体的问题：

> 下一轮如果还想继续推进，应该**从哪里恢复、先复核什么、哪些信号说明不该直接接着改**？

它与现有文档的分工如下：

- `docs/ITERATION_WRAPUP_CARD.md`：回答“这一轮最后几分钟怎么收尾”
- `docs/ITERATION_NOTIFY_PLAYBOOK.md`：回答“成功 / 异常 / 暂停三种结果都必须怎么通知”
- `docs/COLLAB_HANDOFF_CARD.md`：回答“如果换人接手，60 秒内要同步哪些内容”
- **本文**：回答“当下一轮准备重新开始时，如何从上一轮结果安全恢复，而不是直接顺手继续扩大改动”

一句话目标：

> 让后续自动迭代在重新开始时先做“恢复判断”，而不是直接沿着上一次的上下文惯性继续改下去。

---

## 1. 什么时候该看这份文档

适用于以下场景：

- 刚完成上一轮自动迭代，准备开始新一轮
- 你知道仓库里已经有不少未提交改动，担心直接续改会放大冲突面
- build / lint 上一轮是通过的，但你不确定这是否仍足够支持继续推进
- 你已经看过结果通知或迭代日志，想把“下一步怎么安全恢复”变成固定动作

不适用于：

- 当前 `build` 或 `lint` 已明确失败，此时应优先处理首个明确报错
- 当前需要做产品方案权衡、架构改造或多方案取舍
- 当前目标必须改共享类型、状态恢复逻辑、主状态机或持久化结构

一句话判断：

> 当你脑中出现“上轮都做到这里了，那我就接着改吧”这类想法时，先看本文。

---

## 2. 恢复一轮迭代前，先确认哪三件事

### 第一件：当前分支还是不是预期基线

至少确认：

- 当前仍在预期分支上
- 没有切到临时实验分支或错误基线
- 没有出现需要回看历史、强推或重写历史才能继续的前置信号

如果这一步说不清，先不要继续改。

### 第二件：上一轮的结论是否仍然成立

至少复核：

- 上一轮是“成功完成”“异常结束”还是“主动暂停”
- 上一轮停下来的原因是什么
- 上一轮明确说了哪些区域不要继续碰
- 上一轮建议的下一步，是否仍然符合当前工作区状态

如果上一轮是因为“需要用户权衡”而暂停，本轮不要假装这个权衡已经自动完成。

### 第三件：当前工作区脏度是否已经升级

快速观察：

- 未提交文件是否比上一轮更多
- 是否新增了共享类型、API、样式、主页面骨架等核心触点改动
- 是否已经难以在 30 秒内说明现有修改分别属于什么意图

如果答案是“是”，优先收缩目标，而不是继续扩张目标。

---

## 3. 推荐恢复顺序

建议按下面顺序重新开始，而不是跳步：

```text
git 状态 / 当前分支
  → build
  → lint
  → 回看上一轮目标与停手原因
  → 判断本轮是否仍适合继续低风险推进
  → 再决定补文档、改单点文案，还是主动暂停
```

对应到最短动作就是：

1. 检查当前分支与 Git 状态
2. 重新跑 `npm run build`
3. 重新跑 `npm run lint`
4. 用一句话写清“上一轮停在哪、这轮打算从哪恢复”
5. 只选择一个收益明确、边界可控的目标

不建议的恢复方式：

- 直接打开上次改过的文件就继续写
- 因为上轮 build / lint 通过，就默认这轮也安全
- 因为上轮补了文档，这轮就顺手补第二份相邻文档
- 因为已经有很多未提交改动，就把更多改动混进去

---

## 4. 本轮恢复时优先选什么

当上一轮已经留下独立成果，而当前工作区仍较脏时，建议优先级如下：

### 第一优先级：验证后再补一份真正缺口明确的独立文档

前提：

- 当前文档体系里确实缺这一块入口
- 补完后能在 README 或 `docs/DOCS_INDEX.md` 中一句话说清用途
- 不需要顺手改业务代码来“配合文档”

### 第二优先级：单页面、单文件、低争议的文案或可访问性增强

前提：

- 只改一个页面或单个组件
- 不改共享类型
- 不改状态恢复
- 不引入新的持久化结构

### 第三优先级：主动暂停并同步原因

如果出现以下任一情况，暂停比继续更对：

- 这一轮要开始碰多个核心文件
- 需要判断现有未提交改动哪些应保留、哪些应回滚
- 需要在两个以上实现方案间做取舍
- 需要用户决定产品优先级、交互路线或演示侧重点

---

## 5. 哪些恢复信号一出现就该停下

命中任一条，说明“恢复”已经开始滑向“扩改”：

- 本轮目标已经从单点变成了两项以上
- 修改范围开始跨越多个核心页面
- 需要补字段、改共享类型或调整本地存储结构
- 你开始说“顺手把这个也一起做了”
- 你已经说不清本轮收益是什么，只剩“好像还能再做一点”

一句话原则：

> 恢复协议的核心不是帮助你继续做更多，而是帮助你在还能安全继续时继续，在不该继续时更早停下。

---

## 6. 恢复前 30 秒自检

开始前快速确认：

- [ ] 我知道当前分支是什么
- [ ] 我知道当前工作区为什么算脏，或者为什么还不算太脏
- [ ] 我知道上一轮是成功、异常还是暂停
- [ ] 我知道上一轮为什么停在那个点
- [ ] 我知道这轮目标能否用一句话说清
- [ ] 我知道这轮如果继续，会不会碰共享类型、状态恢复、主状态机或持久化结构

如果这 6 项里有 2 项以上答不上来，先不要继续改。

---

## 7. 最短恢复模板

```markdown
- 先重新确认当前分支与 Git 状态
- 重新执行 `npm run build` 与 `npm run lint`
- 回看上一轮结果：成功 / 异常 / 暂停，以及停手原因
- 只恢复一个收益明确、边界可控的低风险目标
- 若范围开始扩大、方案开始分叉或需要改核心结构，则主动暂停并说明
```

---

## 8. 一句话结论

自动迭代最容易失控的时刻，不是刚开始，而是“上一轮刚做完、觉得一切都还顺手”的时候；恢复协议的价值，就是把这种惯性继续改，变成一次先复核再继续的安全动作。
