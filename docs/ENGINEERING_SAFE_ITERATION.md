# LifeScript Engineering Safe Iteration Guide

面向日常自动迭代、提交前自检与低风险优化的工程操作手册。

## 目标

这份文档用于约束 LifeScript 在快速迭代阶段的工程动作，优先保证：

- 小步前进，不破坏现有演示链路
- 先验证，再修改
- 优先做低风险、可回退、可解释的改动
- 避免在工作区已经存在较多未提交变更时扩大冲突面

## 1. 每次迭代前的固定检查

### Git 状态

先看当前分支和工作区是否干净：

```bash
git status --short --branch
git branch --show-current
```

重点关注：

- 是否仍在统一基线分支上
- 是否已经有较多未提交改动
- 是否存在新增但未纳管的文档、资源或配置文件

如果工作区已经有大量业务文件变更，优先选择以下低冲突动作：

- 新增独立文档
- 新增不影响运行的说明文件
- 修复非常明确、影响面很小的问题
- 完善现有操作手册、答辩材料或自检说明

### 工程验证

至少执行：

```bash
npm run build
npm run lint
```

如果需要完整确认：

```bash
npm run verify
```

## 2. 推荐的低风险改动类型

在比赛冲刺期，优先级建议如下：

### A. 工程问题修复

适合处理：

- lint 警告或错误
- 类型不一致但修复路径明确的问题
- 容易复现的边界空状态
- 文案不清晰、提示缺失、空态引导不足

### B. 体验优化

适合处理：

- 搜索与筛选反馈更清晰
- 无障碍标签补充
- 键盘操作更顺手
- 演示路径中的状态说明更明确
- 本地持久化状态的解释更清楚

### C. 小功能增强

适合处理：

- 基于现有状态字段的展示增强
- 已有页面中的轻量统计摘要
- 不影响主流程的新快捷入口
- 帮助录屏或答辩的辅助信息

### D. 轻度重构

仅在以下条件同时满足时进行：

- 不改变外部行为
- 不涉及核心状态机重写
- 不跨多个大文件搬移逻辑
- 改后能立即用 build/lint 验证

### E. 文档完善

当业务文件已经存在较多未提交修改时，文档完善通常是最安全的选择。

推荐补充：

- 演示手册
- 工程自检清单
- 常见故障排查
- 提交前检查说明
- 风险边界说明

## 3. 应避免的高风险动作

以下动作默认不应在自动迭代中进行：

- 重写主状态机
- 大规模改动 `src/app/page.tsx` 这类核心聚合文件
- 同时修改多个核心页面的数据结构
- 未经验证就调整本地存储 key 或恢复逻辑
- 批量重命名公共类型且不做全局验证
- 强推、改写历史、清空用户现有改动
- 引入新的复杂依赖，只为很小的体验问题服务

## 4. 发生已有未提交改动时的处理策略

如果 `git status` 显示已有较多改动，遵循以下原则：

1. 不覆盖用户已有修改
2. 不假设当前未提交内容都来自同一目标
3. 优先新增文件，少改旧文件
4. 如需改旧文件，尽量只改未被频繁改动的独立区域
5. 如果方案需要对现有修改做取舍，应停止并说明原因

## 5. 推荐的单次迭代流程

```text
检查 Git 状态
  → 运行 build/lint
  → 判断是否已有大量未提交改动
  → 选择低风险迭代点
  → 实施最小改动
  → 重新验证
  → 记录本次交付内容
```

## 6. 提交前最小验收清单

- [ ] 已确认当前分支
- [ ] 已查看 `git status --short --branch`
- [ ] 已运行 `npm run build`
- [ ] 已运行 `npm run lint`
- [ ] 本次改动范围足够小，能清楚解释收益
- [ ] 没有覆盖现有未提交业务改动
- [ ] 没有引入新的高风险依赖或结构性破坏

## 7. 比赛冲刺阶段的工程原则

### 优先稳定性，而不是“看起来改了很多”

如果 build 与 lint 已经通过，不要为了做改动而做改动。优先做：

- 提升演示稳定性
- 提升答辩可讲述性
- 提升体验细节完整度
- 补充工程说明和运行边界

### 优先可验证，而不是“理论上更优”

在冲刺期，一项改动最好能在当下立即验证价值，而不是依赖后续连续多轮调整。

### 优先低冲突，而不是“全局最优重构”

当工作区已经不干净时，自动迭代应尽量减少与现有改动的交叉面积。

## 8. 常用命令速查

```bash
git status --short --branch
git branch --show-current
npm run lint
npm run build
npm run verify
```

## 9. 适用结论

对于当前 LifeScript 项目，若单次自动迭代开始时：

- 当前分支正确
- build 通过
- lint 通过
- 工作区已有较多未提交业务文件变更

那么最推荐的动作通常是：

1. 文档完善
2. 明确无争议的微体验优化
3. 不触碰核心状态机的轻量增强

这能最大限度减少冲突，同时保持项目持续向前推进。
