# LifeScript Safe Doc Patch Playbook

用于在 `build` 与 `lint` 已通过、但工作区已经较脏且不适合继续碰核心业务代码时，进一步回答一个更具体的问题：

> 如果这一轮决定继续做文档完善，**优先应该补哪类文档、如何避免重复、做到哪一步就该停下？**

它和现有文档的分工如下：

- `docs/WORKSPACE_DIRTY_ITERATION_PLAYBOOK.md`：回答“工作区较脏时这一轮还能安全做什么”
- `docs/LOW_RISK_CHANGE_CATALOG.md`：回答“哪些改动类型通常更稳妥”
- `docs/DOCS_INDEX.md`：回答“当前已经有哪些文档、分别该在什么场景看”
- **本文**：回答“当你已经决定继续补文档时，应该优先补什么、怎么补、怎样避免重复或空转”

一句话目标：

> 当本轮不适合继续扩展业务代码时，帮助后续自动迭代稳定地产出**不重复、可复用、可索引、可立即服务演示/答辩/协作**的文档补丁。

---

## 1. 使用前提

建议仅在以下条件同时成立时使用：

- 已执行 `git status --short --branch`
- 已确认当前分支是预期基线分支
- 已执行 `npm run build`
- 已执行 `npm run lint`
- 当前没有必须先修复的明确工程报错
- 你已经判断“本轮继续补文档”比“继续改业务代码”更安全

如果 `build` 或 `lint` 失败，优先看 `docs/ITERATION_VERIFICATION_TRIAGE_CARD.md`；如果你还不能确定本轮该不该继续，看 `docs/SAFE_CHANGE_DECISION_TREE.md`。

---

## 2. 什么叫“值得补的文档补丁”

在 LifeScript 当前阶段，值得继续补的文档通常满足以下大部分条件：

- 能直接服务一个明确场景：演示、答辩、自检、交接、通知、自动迭代
- 不需要发明新的产品策略，只是把已有共识整理得更可执行
- 能降低下一轮协作者的判断成本
- 与已有文档形成互补，而不是改头换面重复一遍
- 可以在本轮结束前完成索引补充与记录闭环

一句话判断：

> 好的文档补丁，不是“再写一份差不多的文档”，而是“补上某个已经反复出现、但目前仍缺少低成本入口的操作说明”。

---

## 3. 优先补什么

### 第一优先级：高频但容易遗漏的执行卡 / 速卡

适合场景：

- 每轮都要做，但每次都要重新组织顺序
- 已有较长文档，但缺少 30 秒版本
- 失败、暂停、通知、交接时容易漏字段

典型方向：

- 开始前检查卡
- 停手信号卡
- 通知速卡
- 收尾卡
- 风险分级卡

为什么优先：

- 复用率高
- 收益容易解释
- 与脏工作区下的“低心智负担”目标高度一致

### 第二优先级：把抽象原则落到项目当前语境的场景化说明

适合场景：

- 已有抽象原则，但还不够贴近 LifeScript 当前页面或比赛节奏
- 协作者知道“原则上该怎么做”，但不知道“落到这个项目现在该怎么做”

典型方向：

- 当前页面的低风险候选项清单
- 当前文件 / 组件的安全触点地图
- 单文件微增强边界说明
- 演示场景下的推荐讲述顺序

为什么优先：

- 可以直接把抽象规则变成可执行动作
- 对后续自动迭代选题帮助很大

### 第三优先级：结果同步与协作交接类模板

适合场景：

- 已有结果，但不容易快速同步出去
- 下一位协作者容易不了解“这轮做到哪了、为什么停在这里”

典型方向：

- 通知模板
- 交接卡
- 日志模板
- 最短复盘结构

为什么优先：

- 有助于形成固定闭环
- 可显著降低“做了但没沉淀”的损耗

---

## 4. 默认不要补什么

即使看起来也像“文档工作”，下面这些内容默认不适合在低风险自动迭代里继续扩展：

- 需要你主观发明新产品方向的长篇方案
- 与已有文档核心结构高度重复、只是换个标题
- 需要依赖当前未提交业务改动细节才能成立的说明
- 对多个候选实现方案做取舍，但用户尚未明确偏好
- 把未来也许会做的内容写成看似已经完成的结论

一句话原则：

> 文档完善的价值来自“降低不确定性”，而不是“制造新的不确定性”。

---

## 5. 三步判断：现在补哪一类文档最合适

### 第一步：先问“当前最缺的是什么入口”

快速判断：

- 是缺“从哪里开始”的入口？ → 补检查卡 / 执行卡
- 是缺“做到一半何时停”的入口？ → 补停手信号 / 风险分级卡
- 是缺“结果怎么同步”的入口？ → 补通知模板 / 交接卡
- 是缺“这个项目里具体该选什么目标”的入口？ → 补场景化 backlog / 安全触点图

### 第二步：确认现有文档是否已经覆盖 70% 以上

如果某个主题已经有：

- 完整说明
- 速卡版本
- 索引入口
- 使用场景描述

那这一轮通常不值得再补一份平行文档。

### 第三步：确认补完后是否能立刻接入索引与闭环

一份值得做的新文档，至少应该满足：

- 能在 README 或 `docs/DOCS_INDEX.md` 中一句话说明用途
- 能被后续自动迭代直接引用
- 能在本轮日志中一两句话说清收益

如果补完后你都说不清“以后什么时候打开它”，通常说明这份文档还不够稳。

---

## 6. 推荐结构模板

新增文档时，优先采用下面的轻量结构：

```markdown
# 文档标题

一句话说明：它解决什么问题。

## 1. 什么时候使用
- 适用前提
- 不适用前提

## 2. 它解决的核心判断
- 关键问题 1
- 关键问题 2

## 3. 推荐动作 / 优先级
- 先做什么
- 再做什么
- 默认别做什么

## 4. 停手条件
- 哪些信号一出现就该停

## 5. 最短模板
- 可直接复用的最小写法

## 6. 一句话结论
- 收束原则
```

这样做的好处：

- 风格统一
- 便于快速扫描
- 便于后续继续扩写而不失控
- 更适合在 README 与索引中挂入口

---

## 7. 推荐信息来源

补文档时，优先基于以下来源整理：

- 当前仓库已有 README 与 `docs/` 文档
- 已经被反复执行的自动迭代顺序
- 已经发生过的停手边界与风险共识
- 已通过验证的工程检查结果

不建议把下面这些当作文档主依据：

- 你对尚未实现功能的主观想象
- 尚未确认归属的大量未提交业务改动
- 需要用户拍板的方案取舍
- 没有被当前项目事实支撑的“最佳实践空话”

---

## 8. 做到哪一步就该停

命中任一条就建议停下，不再继续顺手扩改：

- 本轮已经形成一份独立、可索引、可解释的新文档
- README 与 `docs/DOCS_INDEX.md` 已补入口
- 本轮日志已记录目标、验证结果与风险边界
- 下一步开始想写第二份相邻主题文档
- 下一步开始需要顺手修改业务代码来“配合文档”

一句话原则：

> 文档补丁之所以低风险，不是因为它永远可以无限继续，而是因为它能在形成独立成果后及时停住。

---

## 9. 最短执行模板

```markdown
- 当前分支正确，工作区较脏
- build / lint 已通过
- 本轮不继续扩大业务代码改动面
- 选择补一份可独立交付的文档补丁
- 同步 README 与 docs 索引入口
- 记录日志并输出结果通知
```

---

## 10. 一句话结论

当 LifeScript 当前工作区已经较脏，而你又希望继续做一轮积极型自动迭代时，最稳妥的文档路径通常不是“继续泛泛地补文档”，而是优先补上**缺入口、缺速卡、缺场景化落点、缺通知闭环**的那一块。
