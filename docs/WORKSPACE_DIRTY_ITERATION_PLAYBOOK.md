# 工作区较脏时的自动迭代行动手册

用于在 `build` 与 `lint` 已通过、但工作区已经存在较多未提交改动时，快速决定这一轮还能安全做什么、应该怎么收尾，以及哪些动作不值得继续冒险。

---

## 1. 什么时候该打开这份文档

适用于下面这种典型场景：

- `git status --short --branch` 显示当前分支正确，但已有较多未提交改动
- `npm run build` 已通过
- `npm run lint` 已通过
- 你还想继续“积极型自动迭代”，但又不想误伤现有业务修改

一句话判断：

> 当前不是“能不能继续改”的问题，而是“还能安全改到哪一层”。

---

## 2. 先做 30 秒判断

按顺序快速问自己：

1. 当前分支是不是目标基线分支？
2. 工作区里是否已经有很多业务文件处于修改状态？
3. `build` 和 `lint` 是否都已通过？
4. 这次想做的改动，是否会碰核心页面、共享类型、状态机或数据模型？
5. 如果现在停手，是否已经可以交付一份独立成果？

如果前 3 个答案是“是”，第 4 个答案也是“是”，那么本轮更推荐：

- 不继续碰核心业务代码
- 改做独立文档、演示辅助材料、检查卡、交接卡、通知模板
- 或只做极小且边界明确的文案优化

---

## 3. 优先级建议：还能做什么

### 第一优先级：独立文档

最适合继续推进，因为：

- 不需要改动核心逻辑
- 与现有未提交业务改动冲突概率低
- 可以直接形成可交付成果
- 对录屏、答辩、自检、交接都有立刻价值

优先考虑：

- 演示检查卡
- 答辩速答卡
- 冒烟测试矩阵
- 自动迭代执行卡
- 收尾模板
- 协作交接卡
- 故障排查补充说明

### 第二优先级：只影响单页面的轻微体验优化

只有在满足下面条件时再做：

- 改动范围单一
- 不改共享类型
- 不改状态机
- 不引入新的持久化结构
- 不需要跨多个页面联动调整

典型例子：

- 更清晰的空态文案
- 补一条无障碍描述
- 调整已存在提示语的可理解性
- 给现有按钮补更明确的微文案

### 第三优先级：轻度重构

只有在收益非常明确，且你能保证影响面局部、容易复验时才考虑。

如果需要问“这会不会影响多个页面”，通常就不适合在当前这轮做。

---

## 4. 当前不建议做什么

在工作区已经较脏、且 `build` / `lint` 都通过的情况下，下面这些动作默认不建议继续做：

- 重写主状态机
- 修改核心页面间共享类型
- 新增会影响多个页面的状态字段
- 调整本地存储结构
- 批量整理目录或重命名大量文件
- 为了“顺手统一”而扩大改动范围
- 重写历史、强推、覆盖现有修改

一句话原则：

> 当前最危险的，不是没有继续迭代，而是为了“再多做一点”把低风险回合做成高冲突回合。

---

## 5. 推荐闭环：每轮最小动作

如果本轮不再碰核心业务代码，推荐按照下面顺序结束一轮：

1. 检查分支与工作区状态
2. 跑 `npm run build`
3. 跑 `npm run lint`
4. 做一个独立、低冲突的改动
5. 再次复验 `build` 与 `lint`
6. 记录到 `docs/ITERATION_LOG.md`
7. 输出通知，说明本轮目标、结果、风险边界与后续建议

这样做的价值是：

- 有成果
- 有记录
- 有通知
- 有停手边界
- 不会把本轮风险悄悄放大

---

## 6. 什么时候应该直接停下

命中任一条就建议停下并说明：

- 需要在两个以上业务页面同时改动
- 需要修改共享类型或持久化结构
- 需要在多个实现方案中做取舍
- 需要判断某批现有未提交改动到底该保留还是回滚
- 需要和用户确认产品取舍、交互优先级或演示路线

这时最正确的动作不是硬做，而是：

- 说明为什么这已经超出低风险边界
- 列清楚可选方案与影响面
- 等待人工权衡

---

## 7. 最短执行模板

```markdown
- 当前分支正确
- 工作区较脏
- build / lint 已通过
- 本轮继续避免扩大核心业务改动
- 选择交付一项独立文档或低冲突补充
- 完成后再次复验并记录结果
```

---

## 8. 一句话结论

当工作区已经较脏、而工程验证又已通过时，积极型自动迭代最优解通常不是“继续深入改代码”，而是“继续稳定地产出低冲突、可复用、可交付的增量成果”。
