# 高风险脏工作区停手速卡

用于在 `git status --short --branch` 已显示工作区存在**多个核心业务文件并行修改**、且 `npm run build` 与 `npm run lint` 已通过时，快速判断：

> 这一轮是否还适合继续积极型自动迭代，还是应该立即停手、说明边界并通知结果。

---

## 1. 适用场景

当你已经完成下面三个固定检查：

```bash
git status --short --branch
npm run build
npm run lint
```

并且出现以下任一信号时，可直接使用本速卡：

- 多个核心页面同时处于修改状态
- `src/app/page.tsx`、`src/types/index.ts`、`src/lib/memory.ts`、`src/app/api/chat/route.ts`、`src/app/layout.tsx`、`src/app/globals.css` 中有多个文件同时被改
- 业务代码、样式、文档、新增目录同时存在未提交修改
- 你已经无法在 30 秒内说清当前未提交改动分别属于哪个主题

一句话判断：

> 工程通过，不代表还适合继续扩改；当边界已经模糊时，继续加码通常会把风险放大。

---

## 2. 一眼识别：什么叫“高风险脏”

如果同时满足下面 4 条，默认按**高风险脏**处理：

1. 当前分支正确
2. `build` 已通过
3. `lint` 已通过
4. 工作区同时出现多个核心业务文件 + 文档 + 新增目录 / 新文件

典型特征不是“文件多”而已，而是：

- 现有改动可能来自多个目标
- 继续改代码很容易与未提交修改交叉
- 哪怕你只想做一个小补丁，也很难保证不会碰到别人正在改的区域

---

## 3. 高风险脏时，最推荐的动作

### 推荐动作 A：停止继续扩大业务改动面

这通常是最专业的选择。

适用原因：

- 当前工程已经可通过验证
- 继续改业务代码的收益，通常小于潜在冲突成本
- 即使本轮想做的是“低风险小优化”，也可能因为上下文不完整而误伤现有未提交改动

### 推荐动作 B：只交付独立、低冲突成果

如果一定要继续推进，优先考虑：

- 新增独立文档
- 追加迭代日志
- 补充通知模板、检查卡、交接卡、答辩辅助材料
- 做一条结果说明，而不是继续扩改代码

### 推荐动作 C：主动通知并说明停手原因

通知里至少说清：

- 当前分支
- `build` / `lint` 结果
- 为什么判断为高风险脏
- 本轮做了什么低冲突交付
- 为什么停在这里
- 下一步需要什么人工判断

---

## 4. 高风险脏时默认不要做什么

下面这些动作默认不应继续：

- 再进入核心页面补代码
- 顺手扩大到多个组件
- 修改共享类型
- 调整本地持久化结构
- 重写排序 / 筛选 / 状态恢复逻辑
- 为了“再积极一点”继续做功能增强
- 覆盖现有未提交改动
- 强推或重写历史

一句话原则：

> 当你已经需要不停确认“这会不会碰到前面的修改”时，说明这轮最好的动作不是继续改，而是及时停。

---

## 5. 最短判断模板

可直接复用：

```text
当前分支正确，build 与 lint 已通过，但工作区已进入高风险脏状态：多个核心业务文件、样式与文档并行修改，边界不够清晰。本轮不再继续扩大业务改动面，只交付独立低冲突成果并主动通知结果。
```

---

## 6. 最短通知模板

```markdown
- 当前分支：{{branch}}
- Git 状态：工作区为高风险脏，多个核心业务文件并行修改
- 验证结果：build ✅ / lint ✅
- 本轮交付：{{独立文档或记录}}
- 停手原因：继续改业务代码会放大冲突面
- 后续建议：先人工判断现有未提交改动的归属与取舍，再决定是否继续进入业务逻辑
```

---

## 7. 什么时候必须停下等人工判断

命中任一条即可停下：

- 需要在两种以上实现方案中做取舍
- 需要决定现有未提交改动哪些该保留、哪些该回滚
- 需要继续修改核心页面、共享类型或恢复逻辑
- 需要跨多个页面联动修改才能完成目标
- 需要解释“这几批未提交修改到底是不是同一主题”

这些都不是适合自动继续拍板的范围。

---

## 8. 一句话结论

当工作区已经同时包含多个核心页面、共享逻辑、样式和文档修改时，**最好的积极型自动迭代不是继续冒险补代码，而是做出清晰判断、留下低冲突成果，并把停手边界说明白**。
