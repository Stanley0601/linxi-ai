# 脏信号组合判断速卡

用于在 `git status --short --branch` 同时出现多个信号时，快速判断：

> 这轮到底还适合继续做本地低风险增量，还是应该把“已通过验证 + 说明边界 + 主动通知”当作本轮的完整结果？

这个速卡专门处理下面这种**组合信号**：

- 当前分支正确
- `npm run build` ✅
- `npm run lint` ✅
- 但 Git 状态里同时出现两类及以上提醒，例如：
  - `ahead N`
  - `?? 目录/文件`
  - 已有业务文件未提交改动
  - 文档与组件并行修改

它不是替代单张速卡，而是帮助在多个信号同时出现时，先做一次总判断，避免你一条一条都看完后还是不知道本轮到底应不应该继续推进。

---

## 1. 什么时候优先看这张卡

当你已经跑完：

```bash
git status --short --branch
npm run build
npm run lint
```

并且看到的状态不是单一信号，而是类似下面这种组合：

```text
## feat/v12-unified-baseline...origin/feat/v12-unified-baseline [ahead 2]
 M README.md
 M docs/DOCS_INDEX.md
 M docs/ITERATION_LOG.md
 M src/components/EndingView.tsx
 M src/components/MomentsFeed.tsx
 M src/components/TimelineView.tsx
?? docs/ITERATION_AHEAD_SIGNAL_CARD.md
?? docs/ITERATION_UNTRACKED_DIRECTORY_SIGNAL_CARD.md
```

一句话判断：

> 单个信号通常只说明“某一类边界需要注意”；多个信号叠在一起，才更能说明这轮是否已经接近不该继续自动扩改的线。

---

## 2. 为什么组合信号比单个信号更重要

单独看到 `ahead 2`，不一定危险；
单独看到 `?? docs/...`，也不一定危险；
单独看到一个组件文件已修改，仍可能继续做单文件微增强。

但当它们**同时出现**时，意义会改变：

1. **你面对的已经不是单一边界，而是多层边界叠加**
2. **本轮新增动作更容易和既有未提交改动、既有提交边界或未跟踪内容发生耦合**
3. **继续推进时最容易犯的错，不是修坏 build，而是误把“还能做一点”理解成“还适合继续扩改”**

因此，组合信号真正抬高的不是“命令失败概率”，而是：

- 误判当前工作区风险层级
- 继续进入已有 diff 区域
- 顺手扩大到提交策略、历史边界或多主题并行改动
- 明明该停手说明，却为了推进感再补一轮重复建设

---

## 3. 最小组合判断法

### 第一步：先看是不是“验证通过 + 边界变复杂”

如果同时满足：

- 当前分支正确
- `build` / `lint` 已通过
- 但 Git 状态已经出现两类及以上风险提醒

那么这轮的核心问题通常不再是“能不能继续改”，而是：

> 继续改的收益，是否已经明显小于扩大边界的代价？

这时默认应先把判断重心放到**边界清晰度**，而不是“还有没有地方可改”。

### 第二步：再问自己 4 个问题

1. 我能否清楚区分“已有提交”“当前未提交改动”“未跟踪新增内容”分别属于什么？
2. 我这轮准备进入的目标文件，是否没有与现有 diff 明显重叠？
3. 我准备新增的成果，是否是单点、独立、可立即复验的？
4. 如果现在停手，我能否已经写出一条完整、专业的结果通知？

如果前 3 个问题里任意 2 个答不上来，就不应继续扩改。

如果只有第 4 个问题能答上来，往往说明：

> 这轮更适合做收尾闭环，而不是继续追求新增成果。

### 第三步：把当前工作区归到三种结果之一

#### 结果 A：还能继续做单点低风险增量

只在以下条件同时满足时成立：

- 目标文件边界清楚
- 本轮不碰 push / rebase / 历史整理
- 本轮不进入已有 diff 重叠区
- 改完后仍可立即复验 build / lint
- 本轮成果能一句话说清楚，不需要额外方案权衡

典型动作：

- 单文件说明性增强
- 独立文档补丁
- 索引补齐
- aria / 空态 / 演示提示补丁

#### 结果 B：更适合做零代码闭环

当出现下面任一情形时，更适合直接停在这里：

- 候选动作开始撞上已有已修改文件
- 新增成果需要依赖多个信号卡或多份文档互相补入口
- 你已经开始犹豫“再补一点会不会更完整”
- 本轮最有价值的结果其实是“把当前边界说明白”

典型动作：

- 记录当前 Git 状态与验证结果
- 在日志里写清楚为什么停在这里
- 主动通知成功/暂停/异常结果
- 把下一轮建议收敛到可执行的最小判断

#### 结果 C：必须停下等人工判断

命中任一条即可：

- 需要决定 push、squash、rebase 或历史整理
- 需要在多个改动主题之间做人为取舍
- 需要继续进入当前已修改的核心业务文件
- 需要解释 ahead 的提交与当前未提交改动是否属于同一主题
- 需要决定未跟踪内容整体保留还是回滚

---

## 4. 当前这类 LifeScript 信号组合该怎么理解

如果你看到的是下面这种组合：

- 分支正确
- `ahead N`
- README / 文档索引 / 迭代日志已改
- 一个或多个组件文件已改
- 还有新的未跟踪文档

更稳妥的理解通常是：

> 当前工作区已经不是“单点脏”，而是“已有提交边界 + 已有未提交改动 + 新增未跟踪内容”并行存在的组合脏区。

这意味着：

- 继续补纯文档，容易进入重复建设
- 继续进已有组件文件，容易与现有业务 diff 重叠
- 继续碰 Git 层策略，又会越过自动迭代边界

因此，这类组合下最常见的优先级应该是：

1. 先确认有没有**真正独立**的新目标
2. 没有就直接做零改动收尾
3. 只有在目标仍然足够单点、低冲突、可立即复验时才继续

---

## 5. 默认推荐动作

### 推荐动作 A：先把组合信号写成一句结论

推荐先输出类似这样的判断：

```text
当前分支正确，build 与 lint 已通过，但工作区同时存在 ahead 信号、已修改业务文件与未跟踪文档内容；这说明本轮面对的是组合脏区，而不是单一风险点，后续动作应优先判断是否还有真正独立的单点增量，否则应直接收尾并主动通知。
```

### 推荐动作 B：只有“单点、独立、可复验”才继续

继续动作必须同时满足：

- 只进入一个清晰目标
- 不跨多个既有已修改文件
- 不依赖 Git 历史整理
- 不需要用户做取舍
- 改完即可复验

只要其中一条不成立，就更适合停止。

### 推荐动作 C：把“停在这里”当作合格结果

在组合信号场景里，及时停手并说明原因，不是保守，而是专业。

因为真正高质量的自动迭代，并不是每轮都必须新增文件或改代码，而是：

- 先验证
- 再判断
- 能独立推进就推进
- 不能独立推进就明确停手
- 最后主动通知结果

---

## 6. 最短判断模板

```text
当前分支正确，build 与 lint 已通过，但 Git 状态同时出现 ahead、未跟踪内容与已有文件修改等组合信号。这说明当前工作区已进入组合脏区：若本轮仍有单点、独立、可立即复验的低风险增量，可继续一次；否则应把“验证通过 + 边界说明 + 主动通知”作为本轮完整结果。
```

---

## 7. 最短通知模板

```markdown
- 当前分支：{{branch}}
- Git 状态：存在组合信号（如 `ahead N`、已有文件修改、未跟踪内容并行出现）
- 验证结果：build ✅ / lint ✅
- 本轮处理：{{单点补丁 / 零改动收尾}}
- 风险说明：当前工作区属于组合脏区，本轮不处理 push、历史整理，也不继续扩大到已有 diff 重叠区
- 后续建议：若下一步需要进入已修改文件、整理提交边界或处理未跟踪内容归属，应先人工确认
```

---

## 8. 一句话结论

当 `git status --short --branch` 已同时出现 `ahead N`、未跟踪内容和已有文件修改等多种提醒时，最稳妥的理解通常不是“还有很多地方能继续做”，而是**当前工作区已经进入需要优先判断是否该停手的组合脏区**；只有在候选动作仍然单点、独立、可立即复验时，才适合再推进一次。
